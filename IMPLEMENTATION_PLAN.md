Status as of 2026-10-30. Source: the [Sineobex Build & Strategy Plan](https://claude.ai/code/artifact/6f83b7b9-4134-4c36-ad0c-17a41eed3af3) (main tab, the **Build plan** tab dated Oct 19, the **Proposed · Oct 12** tab, and the **Google Doc Contents** field spec). This file turns the Build plan's phases 0–12 into concrete work in this repository: what gets built, on what stack, how each phase is tested, and what still needs a person. Statuses in the phase table are kept current as work lands.

---

## 1. What we are building

A field-first EMR for street medicine teams, piloting in Detroit:

- **Field app** (Flutter, iOS and Android): charting that works with no signal, an encrypted local database, and a sync protocol that deletes local data only after the server confirms each value.
- **Portal** (Next.js, browser, online-only): Logistics, Program Admins and Billing/Data. Route building, configuration, merge queue, attestation, exports, audit dashboard.
- **API** (TypeScript, Hono): the only thing either app talks to. Every permission check and every audit event happens here.
- **Database** (PostgreSQL, plain SQL migrations): runs unchanged on Supabase (preview, made-up patients only) and RDS (pilot, under the AWS BAA).
- **Infrastructure** (AWS CDK): the production stack, checked in CI against the cdk-nag HIPAA Security rule pack.

Out of scope for the MVP, per the plan's V2 list: AI patient story, resource directory (the Resources tab shows Coming Soon), geofenced alerts, team chat, offline desktop, dictation, volunteer run sign-up, referral status and completion tracking, supply barcode scanning, send-out labs.

### Decisions this plan makes, and why

| # | Decision | Why |
|---|---|---|
| D1 | The OpenAPI spec is **generated from the API's Zod route definitions** (`@hono/zod-openapi`), committed to `packages/contract/openapi.json`. TS types (portal) and the Dart client (phone) are generated from that file. CI regenerates all three and fails on any diff. | A hand-written spec can drift from the server. Generating it from the code that validates requests means the contract is the implementation. The Build plan's goal — "the two apps can't drift apart" — holds because CI enforces it. |
| D2 | The Dart client is produced by a **small generator we own** (`packages/contract/scripts/gen-dart.ts`), not openapi-generator. | openapi-generator's Dart output pulls in `dio`, `built_value` and a build step, and is hard to review. Ours emits plain model classes and one client class, only for the shapes we use. |
| D3 | The API core is **runtime-neutral**: `createApp(deps)` takes a database handle, a token verifier, a clock and a blob store. Node and Deno entry files only wire those in. | The plan's "same code on Node, in ECS Fargate" only holds if nothing in the core touches Deno- or Node-specific APIs. Tests run the core on Node against a real Postgres. |
| D4 | All tables live in a **`sineobex` schema**, not `public`; the `anon` and `authenticated` roles get no grants. | On Supabase, PostgREST exposes `public` to the internet. Keeping tables out of it enforces "the phone and the portal talk only to our API" at the database. RDS has no such roles; the migration checks before revoking. |
| D5 | **RLS is the second line**: every request runs in a transaction that sets `app.team_id`; team-scoped tables carry a policy on it. The API connects as a non-owner role. | A handler that forgets a `team_id` filter returns nothing instead of another team's patients. Plain Postgres policies, no Supabase `auth.uid()`. |
| D6 | **Auth accepts any OIDC issuer** via JWKS (`jose`), configured by `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`. Admin and Billing/Data actions require an MFA-level token (`aal2` on Supabase; Cognito enforces MFA at the pool). Tests use a local signing key. | "Supabase Auth swaps for Cognito without touching app screens." The swap is three environment variables plus the MFA claim mode. |
| D7 | **Audit log**: one hash chain per team (`hash = SHA-256(prev_hash ‖ canonical row)`), written in the same transaction as the change it records, serialized per team with `pg_advisory_xact_lock`. UPDATE and DELETE are blocked by trigger and by grants. A job writes each chain head to the anchor store (S3 Object Lock, compliance mode, in production). | Matches module 10. Per-team chains keep one busy team from serializing everyone. Verification is a single SQL walk, covered by tests that tamper with a row and expect the walk to fail. |
| D8 | **Sync protocol** exactly as module 9: immutable change entries (UUID change ID, device record ID, entity, field, value, base version, user, device, device time, per-device sequence, SHA-256 of the canonical value). The server answers each change `accepted` (server version + hash), `rejected` (reason) or `conflict` (server value + version). Field-level purge only after a hash-matched receipt. | The plan's central safety rule. Idempotency by change ID makes "app killed mid-sync" a retry, not a duplicate. |
| D9 | **Draft reconciliation** (Oct 19): a `set` change carries the field version the user saw. Blank or default server field, or matching version → accepted. Different non-blank server value → `conflict`, shown side by side; the user's choice is sent as an explicit resolution and both values stay in field history. | "A field that already holds a different value is never overwritten silently." |
| D10 | **Phone key handling**: a random 256-bit database key per user, wrapped with AES-256-GCM under a key derived from the PIN (PBKDF2-HMAC-SHA256), stored in the platform keystore with this-device-only accessibility. The wrong-PIN counter is written *before* each attempt, so killing the app can't skip a count; the tenth wrong PIN destroys every copy. Biometric unlock reads a second copy from a keystore item the OS releases only after a biometric check against the currently enrolled set (iOS `biometryCurrentSet`, Android Keystore with `enforceBiometrics`). The refresh token is sealed with the database key, so it is usable only after the app is unlocked. | Meets module 9's unlock and wrong-PIN rules. The biometric gate is enforced by the Secure Enclave or Keystore, not by app code; enrolling a new fingerprint invalidates the copy and the PIN still works. |
| D11 | SQLCipher comes from `package:sqlite3`'s build hook (`hooks.user_defines.sqlite3.source: sqlcipher`). | `sqlcipher_flutter_libs` is end-of-life. The hook build is the maintained path, and host tests then run against real SQLCipher, so "the file is unreadable without the key" is a test, not an assumption. |
| D12 | The **portal is a backend-for-frontend**: the browser holds only an encrypted, httpOnly session cookie (no PHI); server components and route handlers call the API with the user's token. Responses carry `Cache-Control: no-store`; patient search uses POST so names never reach URLs, history or access logs; page titles are generic. | Module 9 desktop column: nothing at rest in the browser, no PHI in titles, URLs or history. Internal patient UUIDs do appear in portal URLs so links and the back button work; they identify nothing without a signed-in session. |
| D13 | **Form definitions are data.** `packages/forms` holds the eight categories as typed definitions; they are seeded into `note_type_versions` as platform presets, and the phone downloads the team's versions at sync (bundling the presets for first-run offline). | "Changing an option is a data change, not an app release. Each note type is versioned." |
| D14 | GitHub Actions are **pinned by commit SHA**, Dependabot keeps them current, and every workflow runs with least-privilege `permissions`. | Supply-chain hygiene expected by health-department security questionnaires. |
| D15 | The phone's database is **plain SQL on SQLCipher** through `package:sqlite3`, one file per user and team, opened with the user's raw 256-bit key, `secure_delete` on, synchronous writes. No Drift, no code generation. | Earlier drafts said Drift. The sync engine decides whether records are lost (risk 3), so every statement that confirms or purges should be readable in review, not generated. Separate files per user and team make "locked to that user" structural and make a remote wipe a file deletion that needs no key. |
| D16 | A second offline edit to a field names the first (`follows`). The server accepts it when that change, by the same person, is what last wrote the field, or when its receipt left the field at the current version. | Without it, a person's own unconfirmed edit looks like someone else's value and their next edit conflicts with themselves. |
| D17 | A change the server holds in **quarantine** leaves the phone once the receipt's hash matches, and is listed as "sent to a Program Admin to review". | Module 9's "never dropped" rule exists so the worker can fix a rejection. A quarantined change is one the worker can't fix; the server already holds that exact value for the admin, which is the confirmed-receipt rule. |
| D18 | The clock check reads a **boot clock that counts deep sleep** through the app's own platform channel (Android `elapsedRealtime` and `BOOT_COUNT`, iOS `CLOCK_MONOTONIC` and `kern.bootsessionuuid`). The server time is taken at the middle of each sync request. | Dart's `Stopwatch` stops while the phone sleeps, so a phone left in a pocket would look like its clock drifted and charting would pause for no reason. The midpoint halves a slow network's error. |
| D19 | When a rejected create is fixed, the record's later edits (pending, or rejected only because the record didn't exist yet) are folded into the fixed create, and the server settles their rejections with it. | Edits travel in the same batch as their create, so one bad create would otherwise leave several rejections the worker can't fix one by one. |
| D20 | **Sign-out erases nothing unless every team database on the phone is known to be fully synced**, which needs the key in memory. A sign-out from the lock screen, or with any team's work waiting, keeps the PIN-wrapped key and the files. Only a remote wipe and the tenth wrong PIN (whose key is already gone) delete unsynced data. Kept data stays wipeable: on every lock, wrong PIN, sign-out and app start, and every 5 minutes while nobody is unlocked, the phone asks with each database's device key whether to wipe it, for every database on the phone, whoever it belongs to. Only an explicit wipe order deletes anything; a status the app doesn't know keeps the data, and "wiped" means the device ID is spent (the data stays and syncs under a new one). A wipe is written down before it starts and confirmed to the server whenever it can be, so one the app didn't finish completes later, and a file is never opened while its wipe is unfinished. | The review found four paths where a sign-out erased unsynced records: from the lock screen, after "Wait" when the app locked, and for a second team's database. Making the session the single place that decides, from the files on disk, closes all of them at once. The second review found that kept data then escaped remote wipe, which a lost phone must never do. |
| D21 | When the server confirms (by device key) that the user was removed, the phone **freezes the store** (no new change, audit entries included), uploads every unconfirmed change, and wipes only once the server holds each change ID with a matching hash. Every step re-checks that the same team is still open, and the wipe always targets the database the check started from. A team that dropped out of the person's profile gets the same hand-over at the next unlock. Activity log entries in a hand-over are written to the audit chain as the person's (they are nobody's to approve). A change the server refused as unreadable can't be handed over, so a file holding one is not wiped on removal: it stays, locked, until an administrator orders the wipe, and the person is told. A change already held for review is never applied by a later push from its phone; only the admin's decision puts it on the chart. Nobody decides on their own quarantined change, and a phone with a wipe order, or whose person has 5,000 items waiting from all their phones together, hands nothing more over. A change to a record that isn't on the chart because the same person's create of it waits for review (or a note on such an encounter) is held for that review too (`awaiting_review`) rather than refused; the admin decides each item with its own audit event, the record first, and the queue lists items in the order the phone made them. An accepted fix or choice settles every rejection or conflict it covers: what the phone folded into it on that field, and the person's own earlier attempts linked by `supersedes`/`conflict_of` in the same team. | A change saved during the upload would have been wiped unsent, and a team switch mid-check wiped the wrong team. A read that can't be logged is refused too: what can't be audited can't be shown. Refusing a change because its record waits for review told the clinician the record no longer existed, and nothing could fix it. A rejection left open by a fix of a fix kept the devices page counting work the phone no longer held. |
| D22 | Between checks, the clock status and change stamps are carried forward from the last server time on a clock that runs with the app, and suspended when it goes to the background. A server time whose round trip took over 30 seconds is not used. "Check again" asks the server for its time. | A clock that jumps while the app is open is caught at once instead of up to 20 seconds later, and a reply that trickles in on weak signal no longer pauses a phone whose clock is right. |
| D23 | **An encounter stays on the phone while a note on it is in use.** The purge keeps an encounter (a downloaded copy past 24 hours, or one that was closed) while the person has a note on it that is open or has changes waiting; once the note has synced and closed, the encounter follows its own rule again. A note too large for one create (64 KiB) goes as a create with the fields that fit, followed in the same push by the rest as edits at version 0, both when it is created and when a refused create is fixed. | A teammate's encounter opened to chart a note on it expired after a day offline and left the note without its encounter and patient. Marking it as the person's own work would have kept it until they closed it, long after the note was done. A fixed create holding every field could exceed the API's value limit, so the note could never leave the phone. |
| D24 | **Sync gets through weak links and says what the phone really holds.** A request body gets 20 s plus its time at 16 KiB/s. A push or hand-over chunk that times out goes again with half as many changes and bytes, down to one, and each answer doubles that back; only a timeout shrinks it. When the server's stored report of unsynced work is out of date and nothing more can be sent, the phone sends one push with no changes. A sync ends with any batch's own outcome, so a wipe order, lost access or a spent device ID on a later batch is acted on. A refused push backs off like any other failure. While a removal's hand-over can't finish, the phone sends no pushes; after each backoff it asks again with its device key, sends only what the server doesn't hold yet, and still carries out a wipe order, finishes the hand-over, or unfreezes if access came back. | On EDGE or weak 3G every full batch timed out and was resent at the same size, so nothing ever synced and a removed person's phone never handed over. Each push reports what the phone held before its batch, so the devices page and wipe panel said work the server already had would be lost. A stuck hand-over was uploaded again, megabytes at a time, every 20 seconds. |
| D25 | Patient-side records ride the existing change protocol as **seven entities** (`patient`, `patient_alias`, `patient_allergy`, `patient_consent`, `problem`, `problem_note`, `id_link`), and **the permission is checked per entity** (`ApplyActor.permissions`, existing keys only) instead of one `encounters.chart` flag. Parents are checked for creates and for sets whose value names a record (a problem status's encounter, an encounter's patient), on the server and in `_classify`. | Every rule the phase 2 reviews hardened (receipts, fix chains, holds, hand-over) applies to patients unchanged, and a CHW can register patients without being able to chart. A parent the server lacks must be a stale reference or a hold, never a constraint firing inside a push. |
| D26 | **Reconciliation is chosen by field class.** Drafts keep D9's side-by-side conflict. Patient demographics **keep both values**: the change is accepted, the other value is kept in history, a field review opens, and the receipt carries the chart's value. Legal name and birth date accept a fill only from someone who saw the current value (or into a blank); a stale fill is kept as an alternate for an admin, and an estimate is refined only within `ESTIMATE_RANGE`. Aliases, allergies, consents and problem notes are union records; retractions are set-once; work arriving for a problem marked entered in error is kept in its history. A followed change that was kept rather than applied never counts as "saw current" (D16 exception). | Module 9 names a different rule for shared patient fields than Oct 19 does for drafts, and a disagreement about someone's usual area must not sit in Needs attention or block a route. A fill that never saw an admin's correction must not undo it (Oct 19). Without the D16 exception, a second offline edit would overwrite the chart silently. |
| D27 | **A merge moves nothing.** Each patient row keeps a maintained `canonical_id`; every chart read groups by it, and a schema test lists every table with a `patient_id`. Late creates naming the merged ID are stored as sent; late field edits are redirected to the survivor; undo recomputes `canonical_id` and is refused while a later merge sits on top. **The server's redirect lists are authoritative on the phone**: the index's first page carries the complete list and each chart bundle the list for its IDs, and they replace receipt-learned rows, so an undo reaches every phone. | A merge writes only patient rows, so it never contends with pushes on child tables, and undo is exact by construction, records that arrived after the merge included. A redirect learned from a receipt would otherwise outlive an undo and attach new work to the wrong person. |
| D28 | **One match formula, implemented in TypeScript and Dart, pinned by vectors generated from Postgres.** SQL (`patient_candidates` over trigram, Double Metaphone and token GIN indexes led by `team_id`) and the phone's FTS5 trigram table only retrieve candidates, **ranked before they are cut**; a birth year orders ties and never retrieves on its own. Double Metaphone is server-only; nicknames and the accent map are generated data. | Search and duplicate warnings must agree between phone and server, and that must be a test. An unordered cut drops the real match at random once a year range alone fills the limit. |
| D29 | **The team index goes to roles with `patients.view` and a field permission, holds no legal name, nothing derived from one, no token and no clinical content, and is versioned, keyset-paged, staged and swapped in one SQLite transaction.** It expires 7 days after its last refresh and is deleted at every sign-out (a secure-store marker covers sign-out from the lock screen) and on a 403. FTS5 `secure-delete` is on, so deleted names leave no trigrams in the file. | Minimum necessary for the largest PHI store on a phone, and a download that survives EDGE and dead zones without ever exposing half an index. SQLite's `secure_delete` pragma does not reach FTS5 segments. |
| D30 | **The route cache is the existing `records`/`fields` plus `cache_scopes` (`opened`, later `route`), with local work as an implicit scope.** Phase 3 caches only charts a person opened or worked on (no "Keep for today" pins; routes replace them in phase 7), for 24 hours; the purge removes a chart's search rows and ID link tokens with it. Charts download in D24-style batches (10, halved on a timeout to 1, doubled after each answer, up to 50), gzipped. | Offline edits need field versions, the purge needs one more condition, phase 7 adds a `route` source without touching the purge, and nothing of a chart outlives its 24 hours. A fixed 50-chart bundle never finishes on EDGE. |
| D31 | **ID link tokens are 128 random bits, base64url, stored as plaintext and SHA-256 (every lookup by hash) and carried in the URL fragment.** The phone issues links through the `id_link` sync create, online or offline. The handshake locks the patient group's active links, accepts when the phone's `replacesLinkId` is still active anywhere in the group, retires every active link in the group for the winner, and inserts the new link with its final status (`on conflict (token_hash)` only). A conflict goes to the newer `effective_at`; the loser is accepted as retired and both issuers and the admins are told. A link for a merged patient is rejected. | Copy ID link must keep working for anyone on the team; the fragment keeps the token out of every server log; one code path on the phone; the PRD's conflict and merged-patient rules; a multi-target `on conflict do nothing` would have swallowed the one-active index. |
| D32 | **Patient-side writes, and encounter writes that name a patient, take the team's audit-chain advisory lock first; merges and undos lock patient rows `FOR NO KEY UPDATE`.** | It is the lock every audited write already takes, so it adds no contention; an encounter insert's FK check holds `FOR KEY SHARE` on the patient, which `FOR NO KEY UPDATE` never waits on, so a merge and a push have one lock order and can't deadlock; duplicate matching always sees a concurrent create. |
| D33 | **Every patient read goes through one projection; a role searches only by fields it can see; audit details carry IDs, counts and hashes, never names, birth dates, search terms, tokens or comment text; events that disclose several patients list them in `details.patientIds` (GIN-indexed)**, including offline searches (up to 50) and `merges.viewed`. The one exception is an index page, which records its exact ID range (`after`, `next`, version) instead of up to 1,000 IDs: a patient's access report finds every page whose range held its ID after it was registered. A refusal (409) carries codes, IDs and versions only. | Minimum necessary becomes a function, not a screen rule, and each patient's access report finds the searches, match checks, listings and index downloads that showed them, without multiplying audit volume by the team size on every refresh. A 409 thrown inside the transaction rolls back its audit, so it must disclose nothing. |
| D34 | **Registration consent is required in the patient create and stored append-only (`patient_consents`); "unable to consent" creates the chart with a banner; "declines" creates nothing.** | The server enforces consent in the create's transaction, later decisions union without reconciliation, and care is never blocked. |
| D35 | **The clock pause covers problems, problem notes and ID links (and, as before, encounters and notes), not intake, demographics, aliases, allergies or consents.** An intake that asks for a card while the clock is off saves without the link. | ID link conflicts are decided by device time; registering the person in front of you is not medication timing. |
| D36 | **Problem status: the latest observation by corrected device time wins, every observation is a history row, and only `patients.reverse_resolved` moves a problem out of Resolved.** A worker who disagrees adds a new entry (a recurrence, or a reversal request) that an admin reverses and merges in the portal. | The PRD's flow, with no backward write from a phone, and the bag check stays right while the admin decides. |
| D37 | **No new permission keys** (project lead). Every check maps to the 23 keys of `0002`: the team index on a phone needs `patients.view` plus one of `patients.edit`, `encounters.chart`, `checkins.create`; undoing a merge needs `patients.correct_identity`; viewing the problem list needs `patients.view` plus `encounters.chart` or `billing.view_codes`; adding or changing a problem or a note needs `encounters.chart`; Resolved back to Ongoing needs `patients.reverse_resolved`; reviewing duplicates needs `patients.review_duplicates`; legal name and DOB corrections need `patients.correct_identity`. The CHW preset therefore sees no problem list. | PRD module 1: custom roles use "any combination of the existing permissions; no new permission types in the MVP (Oct 12)". Undoing a merge is an identity correction, admin-only by default. |
| D38 | **Billing/Data follows the PRD**: it views charts, ICD-10/CPT codes and supply logs and runs exports; it does not see sensitive details (Oct 19), and gets no team index on the phone. Nothing narrows it further. | The PRD's role table; no PRD text gives a reason to hide more, and Billing/Data holds no field permission. |
| D39 | **A merge retires no card** (project lead). Every active token in the merged group keeps opening the surviving chart; the partial unique index keeps one active token per patient record. Regenerating, online or offline, retires every active token in the group and issues one, so from then on the group has one; the handshake accepts when the old token the phone named is still active anywhere in the group. Undoing a merge gives each record back its own tokens as they stood. A deliberate reading of module 2. | The PRD invalidates a token only when staff regenerate it, and the patient may be carrying either card. |
| D40 | **No legal name on the phone outside a chart** (project lead). The team index and the phone's search table hold no legal name and nothing derived from one (no trigram rows, no phonetic codes), only the PRD's list. A legal name appears on the phone only inside a chart the person opened, kept for today or is working on (24-hour expiry), never in a result list or the duplicate panel; the chart's search rows purge with it. | Module 2's index list, and minimum necessary for a lost phone. |
| D41 | **Search text is not stored in the audit log**, online or offline; the log records which patients a search disclosed, with who, when, the criteria and the count. PLAN-OPEN for counsel. | Minimum necessary; the chain is permanent and can't be redacted. |
| D42 | **A rejection never stops a phone's queue.** Rules that span fields (someone must stay recognisable) are checked on the row the write would leave, and a race the worker can't fix is accepted as history with a notice. Every change also applies inside a savepoint: an integrity-constraint error becomes a stored `server_constraint` rejection, while a transient error still stops the batch for a retry. | `push.ts` stops at a throwing change and the phone resends it first, so one constraint error would block that phone forever; module 9 also makes any rejection a hard stop on the next route confirmation. |
| D43 | **Name normalization is pinned in the repository, not taken from the database.** `sineobex.normalize_name` is generated from `packages/contract/data/unaccent-latin.json` (migration 0015), the same map the API and the phone read; refreshing the map is an explicit generator step. | Postgres 17's `unaccent` dictionary differs from 16's, so keys stored by one version stopped matching the phone's and the API's on the other; CI caught it on the Postgres 17 job. |

## 3. Regulations and standards, and where each is met

Full mapping in `docs/compliance/` (added in phase 0, extended each phase). I am not a lawyer; counsel confirms the legal items listed in section 7.

| Requirement | Where it is met |
|---|---|
| HIPAA §164.312(a) access control: unique user IDs, emergency access, automatic logoff, encryption | OIDC identities per person; per-team role + credential checks in the API on every call; 15-minute portal idle logoff, team-set phone auto-lock (default 5 min) and a 15-minute ceiling; SQLCipher on the phone, KMS on RDS and S3 |
| §164.312(b) audit controls | Hash-chained, append-only audit table; every new action writes its event in the same transaction; anchors in S3 Object Lock; admin audit dashboard with unusual-access flags |
| §164.312(c) integrity | Hash chain; SHA-256 receipts on every synced value and every photo; signed notes change only by addendum or correction, with the old value kept |
| §164.312(d) person or entity authentication | MFA by authenticator app or passkey, no SMS; device registration key for quarantine uploads; re-authentication before exports |
| §164.312(e) transmission security | TLS 1.2+ only; HSTS on the portal; S3 bucket policies deny non-TLS |
| HIPAA minimum necessary (§164.502(b)) | Team search index holds only identifying fields and allergies; Billing/Data never sees sensitive sections; sensitive exams need an extra permission |
| 42 CFR Part 2 (pending counsel) | Behavioral health, harm reduction and reproductive modules sit behind a `view_sensitive` permission so they can be restricted further without a schema change |
| HIPAA Security Rule risk analysis | Template in `docs/compliance/risk-analysis.md`; a person completes it before the pilot |

### How each phase is run

Design first (`docs/design/phase-<n>-<name>.md`, critiqued against the PRD and the code), then units in dependency order with disjoint files, then an adversarial review whose findings are fixed with regression tests, then the decisions move into the D-table above and the status here is set to Done. `CLAUDE.md` at the repository root has the working rules, commands and how helper agents run units; a session picking up a phase starts there and at the design's **Status** section.

### In every phase

- Every new action writes its audit event, in the same transaction. A test helper asserts the event for each new endpoint.
- No patient details in logs, crash reports, notifications or URLs. The API logger accepts allowlisted keys only; the PHI guard in CI fails the build on `console.*` in API code and on realistic-looking identifiers in fixtures.
- Accessibility checks on every new screen, in all three themes.
- Tests for the offline path of every new feature, not only the online one.

## 8. Risks and where I disagree with the plan

1. **The clock check can block care.** Module 9 pauses charting when the phone is more than 5 minutes off server time, while the same module says no rejection ever blocks charting the patient in front of you. With the reference built from last-sync time plus uptime, the pause only fires if someone changes the phone's clock, which is rare, but when it fires it stops a clinician mid-visit. I built the decided behaviour, plus the reboot exception in section 6. My recommendation is to switch to "correct and flag" (P17 as originally proposed) after the preview, once there is data on how often it fires.
2. **Two runtimes for one API.** Running the preview on Supabase Edge Functions (Deno) and production on Node means the Deno entry can break without the Node tests noticing. Mitigation: the core is runtime-neutral and CI type-checks the Deno entry. If the preview stays on Supabase for long, consider running the Node container there too.
3. **The sync engine is the product.** It decides whether clinical records are lost. It has the most tests in the repo, and the Dart engine is tested against both an in-memory fake and the real API in CI. Any change to it should get a second reviewer.
4. **PBKDF2 in pure Dart** (D10) uses 120,000 iterations so unlock stays under a second on older phones. That is below OWASP's 600,000 for PBKDF2-SHA256; it's acceptable only because the wrapped key never leaves the platform keystore. Measure on the pilot's actual phones and raise it, or move to the platform-accelerated KDF in `cryptography_flutter`, before real PHI.
5. **The phone's native code has no automated test yet.** The boot clock and the iOS backup exclusion live in `MainActivity.kt` and `AppDelegate.swift`. CI compiles the Android side; nothing builds the iOS side, because that needs a macOS runner. Before the pilot, add an iOS build job and a device test that the clock check survives sleep and a reboot.
6. **Server answers are trusted on TLS alone.** A wipe order, a removal answer or a receipt whose hash matches makes the phone delete data, and none of them is signed by the server. Anyone the phone trusts to terminate TLS (an MDM or corporate inspection root on iOS, where user CAs can't be excluded as on Android) could forge one. The review judged this hardening rather than a defect, and I agree it needs a trusted root on the phone. My recommendation: pin the API's public key on both platforms before real PHI (phase 12, once the production certificates exist), and consider signing the destructive answers with a key that ships in the app.
7. **The in-memory sync server mirrors the API's rules by hand.** It is what most engine tests run against. It now applies the API's create, field, audit and request-schema rules, and the live job runs rejections, fixes, keep-server choices and large numbers against the real API, but a rule added to the API and not to the fake would still go untested on the phone. Any change to `services/api/src/sync` should come with the same change in `apps/mobile/test/sync/fake_server.dart`.
8. **Scope.** Phases 1–10 are a large build for a small team. If time runs short, cut from the edges (grant report variants, follow-ups board filters), never from sync, audit or permissions.
