# HIPAA Security Rule: technical safeguards mapped to code

Sineobex is a business associate of each customer team. This page maps the Security Rule's technical safeguards (45 CFR §164.312) and the parts of the administrative and physical safeguards that software can support to where they are implemented. It is evidence for the risk analysis and for procurement questionnaires, not a legal opinion; counsel confirms the open items.

Status: **Done** = implemented and tested in this repository. **Partial** = implemented with a stated gap. **Planned** = phase named. **People** = needs a person, a contract or an account.

## §164.312 Technical safeguards

| Standard | Requirement | Implementation | Status |
|---|---|---|---|
| (a)(1) Access control | Allow access only to authorized persons | Every API call verifies an OIDC token, resolves the user's active team membership, and checks role permission and clinical credential before touching data (`services/api/src/auth/`). Row-level security on team-scoped tables is a second line (`db/migrations/`). Each synced patient record is checked against the permission for its own kind, and one function decides what each role receives of a chart (`services/api/src/patients/projection.ts`; `access-policy.md`). Phase 4's sync checks the clinical credential too: a change to a Medical note needs one that charts Medical, and a medication answer one that orders, read from the membership when the change arrives, or the change is held for a Program Admin; and one function decides what each reader receives of a note (`visibleAnswers`, `packages/forms`), the review queue included. Phase 4's online routes check their key first; co-signing and attesting also check the credential, read again once the team's write lock is held, and refuse anyone who wrote, completed or acts as the author of the note; the visit read, the timeline, the queues and the EMS handoff give each note by the same function, from one copy of each read rule that the sync read shares (`services/api/src/encounters/read.ts`). | **Done** (phases 1 and 3; API tests and portal e2e); phase 4: sync and online routes built, screens to come |
| (a)(2)(i) Unique user identification | Required | One identity per person in the OIDC provider (Supabase Auth, then Cognito), bound to the user row at invite by subject, never matched by email; no shared logins; owner registry in `platform_owners`. | **Done** (phase 1) |
| (a)(2)(ii) Emergency access procedure | Required | Platform owners can appoint a replacement Program Admin; procedure in the access policy. | People |
| (a)(2)(iii) Automatic logoff | Addressable | Portal: 15-minute idle sign-out with a warning and a way to stay signed in (`apps/portal/src/proxy.ts`, `IdleWarning`); every read and act the portal makes for the person also refuses a session idle that long, or more than 12 hours old (`api()` in `apps/portal/src/lib/api.ts`, phase 4), since the proxy's gate lets a request through that says it is a prefetch. Phone: auto-lock after 5 idle minutes (team-settable, capped at 15) and after 30 seconds in the background; the app switcher shows a cover (`lib/security/idle_lock.dart`). | **Done** (phase 1) |
| (a)(2)(iv) Encryption and decryption | Addressable | Phone: SQLCipher (AES-256) with a random per-user key wrapped by the PIN and held in the platform keystore (this device only); opening refuses to run without SQLCipher; deleted values are overwritten (`secure_delete`); database files are kept out of device backups (`apps/mobile/lib/sync/local_db.dart`, tests read the file and expect no readable text). Server: RDS and S3 encrypted with KMS. Portal: no PHI at rest. | Partial: phone done (phase 2); server in phase 12 |
| (b) Audit controls | Required | Hash-chained, append-only audit table written in the same transaction as each action (`db/migrations/0003_audit.sql`); refusals are logged too, a request for a team the person is not an active member of, or for a suspended team, included: since phase 4 (`7f12515`) the team scope writes each as `access.denied` to the platform chain, which only platform owners read, with the rule, the route's pattern (never the path, which can carry a patient ID) and the team tried, and a request whose refusal can't be logged fails; search and tamper check in the portal. Every search, duplicate check, chart view, history view, ID card read, merge, undo and correction is logged with the patients shown, and never the search text; the log can be searched by patient, including records merged into that patient (phase 3). Phase 4's sync logs each signature, addendum, correction, declined amendment request, reopen, referral and change kept in a finished note's history in its change's transaction, by note and patient, with field paths and never an answer or a reason's text, and each note, signature, addendum, correction and referral a phone reads, as a view; a phone logs its own offline reads of visits and notes the same way, each record it shows as a view in the transaction that reads it, and they join the chain at the next sync. Phase 4's online routes log each visit, note, signature, addendum, correction, attestation and record made at a visit they show, as a view; a chart's earlier visits, the queues and the lists of notes not complete as one view naming the patients shown; each co-signature, attestation and assignment, never an assignment's reason; and each EMS handoff export with its patient and the notes in the file. A refusal of access is logged with the reason's name; a request for a fresh sign-in, an answer about a record's state, input a route can't take and a record the team doesn't have are not. Home's counts name no patient and log nothing. Anchoring to S3 Object Lock and CloudTrail come in phase 12. | Partial: chain, search and verification done; anchoring in phase 12 |
| (c)(1) Integrity | Protect from improper alteration or destruction | Every synced value is confirmed by SHA-256 of its canonical JSON before the phone deletes it; a field that holds a different value is never overwritten silently (conflicts are shown side by side, and every accepted value is kept in `field_history` with the one it replaced and who approved it). A finished note never changes: a later edit is kept in its history, unapplied, and the person who sent it and the note's author are told; the phone refuses such an edit before sending it when it knows the note is finished (phase 4's phone store); a correction writes each new value as a correction, keeps the old one, and leaves the note signed only while someone who may sign covers what it says; addenda are append-only (phase 4's sync); a co-signature or an attestation made online is written under the team's write lock, for all of a visit's waiting notes or none, and changes no answer (phase 4's routes). Photos in phase 8. Patient details two people recorded differently are both kept until someone chooses; a recorded legal name or date of birth changes only by a logged correction with a reason; merging duplicate charts moves no data and can be undone (phase 3). | Partial: sync and patient records done (phases 2–3); notes' sync, the phone's store and online signing built in phase 4 |
| (c)(2) Mechanism to authenticate ePHI | Addressable | Hash chain verification (`sineobex.verify_audit_chain`, tests tamper with rows and expect detection); per-change receipt hashes on sync, computed by the server from what it stored and compared on the phone (`services/api/src/sync/apply.ts`, `apps/mobile/lib/sync/sync_engine.dart`; shared test vectors). A signature carries the SHA-256 of exactly what its signer saw; the server hashes what it holds and refuses the signature when they differ (`services/api/src/encounters/content-hash.ts`, its Dart twin, `packages/contract/test-vectors/note-content-hash.json`), and the phone makes none, writing nothing, when the note changed after the summary screen drew it (phase 4's phone store). A co-signature or an attestation made online carries it too, and is refused, with nothing written, when the note changed after it was read (phase 4). | **Done** (phases 1–2); signatures in phase 4's sync, phone store and online routes |
| (d) Person or entity authentication | Required | MFA by authenticator app (TOTP, no SMS) for everyone: the API refuses team data without an aal2 token. Admin actions need a sign-in within 15 minutes (step-up in the portal), and so does the EMS handoff export (phase 4). Each phone registers an Ed25519 key per team; wipe checks, wipe confirmations and quarantine uploads are signed with it and verified by the API (`services/api/src/sync/devices.ts`). | **Done** (phases 1–2) |
| (e)(1) Transmission security | Guard against unauthorized access in transit | TLS only. API sends HSTS; Android forbids cleartext and user-installed CAs; S3 policies deny non-TLS. | Partial: API headers and Android config done (phase 0); S3 in phase 12 |
| (e)(2)(ii) Encryption in transit | Addressable | As above. | Partial |

## Privacy Rule touchpoints

| Requirement | Implementation | Status |
|---|---|---|
| §164.502(b) Minimum necessary | Server copies of records on the phone expire 24 hours after download (an encounter the person has a note open or unsynced on is kept until that note has synced and closed); local work is purged field by field once confirmed and closed (phase 2). A draft note stays on its author's phone until it is finished and confirmed, so it can be completed with no signal, or until nobody has changed it for 7 days, counted only by a clock the phone has checked (phase 4). The phone's patient list holds identifying fields and allergies only, no legal name, for field roles only, for 7 days, and is deleted at sign-out; each role receives only its part of a chart; Billing/Data never holds the list or sees sensitive problems; ID card links are sent only to screens that show them (phase 3; `access-policy.md`). A note reaches a reader with only the answers they may see, and a change that would reveal a hidden answer is held for review (phase 4's sync and online reads). The EMS handoff PDF, a file that leaves the team, names the patient by preferred name, age and allergies, never by the legal name or the birth date, and holds no note of a sensitive type, sensitive exam finding, substance use treatment record or sensitive diagnosis, whoever exports it (phase 4; the clinical team and counsel decide, lifecycle 12.1 #27 and #29) | **Done** for patient records (phases 2–3); later modules add their own rows |
| §164.520 Notice of privacy practices | Intake records whether the person was given the notice, with a reason when not; it never blocks registering them. The notice's text and its delivery are the customer team's | Partial: the record is done (phase 3); the notice is People |
| §164.526 Right to amend | A correction to a legal name or date of birth records whether the patient asked for it, the reason and who decided; a declined request is recorded too, with its reason (phase 3). Amendments to notes use addenda and corrections: a patient's request is a correction marked as requested, and a declined one is stored with the value asked for and its reason, and logged (phase 4's sync) | Partial: identity done (phase 3); notes' sync built in phase 4, the screens to come |
| §164.528 Accounting of disclosures | Exports are logged with who, what and when. The EMS handoff export (phase 4) is logged with who, when, the patient and the notes in the file, and every page of the file says who exported it and when | Partial: the EMS handoff export (phase 4); the exports of phase 10 to come |

## Not HIPAA, but in the same evidence pack

- **42 CFR Part 2:** substance use treatment records may need stricter handling. Sensitive modules sit behind a separate permission, and so do problems with sensitive diagnosis codes (phase 3); in a note, the substance use treatment part also needs a clinical credential, and a diagnosis on the sensitive list takes its entry or section with it (phase 4's sync); the EMS handoff PDF holds no treatment record, no sensitive diagnosis and no note of a sensitive type, whoever exports it (phase 4). Counsel decides whether Part 2 applies.
- **WCAG 2.2 AA / ADA Title II / HHS §504:** see `accessibility.md`.
