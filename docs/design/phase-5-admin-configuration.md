## How this phase is built (decided Nov 21)
The project lead decided on Nov 21 that the frontier model builds this phase with helper agents, from the card index, as phase 4 was built (`docs/design/phase-4-encounters.md`, "How this phase is built (decided Nov 16)"). The cloud container has no model runner or GPU. What that changes:

- **The card list of section 13 stays the work-list.** Each row's files, needs and order hold. No card is written in full, so there is no `docs/plan/phase-5-admin-configuration/` folder: section 13 is the index. `tools/card-run.mjs` is not used: the plan's "Which model" trial (`docs/plan/README.md`) moves to the first phase built from cards.
- **The order of section 13.1 holds**: P0 lands first, alone, with CI green, and at most two units are built at once (`CLAUDE.md`), each pair owning disjoint files but for the shared files 13.2 orders. A migration is pushed only after its review; other code may land first and take its fixes as later commits.
- **A unit is built from the design sections its rows point to**, tests first, by one agent in its own worktree (`CLAUDE.md`, "Running units with helper agents"). Each unit's commits are also pushed to `claude/p5-wip-<unit>`, never merged; the project lead deletes those branches when the phase lands.
- **What a card's checks gave is replaced.** Every rule is removed by a script to see its test fail. Each unit gets an independent review, each confirmed finding shown by a failing test before it is fixed. The whole-phase adversarial review at the end is unchanged.
- **Levels still say where review is strictest.** An X row gets the coordinator's second review. What only a small model needs (a card's length, how much it may read, line ranges a driver fetches) does not apply here; unit order, who owns each file and each rule, which units run side by side, and each row's needs do.
- **Nothing is asked of a person mid-build** (the project lead, Nov 21: "everything that needs human decision making should be called out in a document for review after full mvp creation"). Wherever a choice needs a person, the default of section 11 is built, marked `PLAN-OPEN` in the code where the PRD leaves it open, and listed in `docs/decisions-for-review.md` with who decides, the default built, the recommendation, what a later change costs and where it lives. That document is published for review once the MVP (phases 5 to 10) is built.
- **The same method for phases 6 to 10, by default.** No machine here can run the small model. This method is the default for phases 6 to 10 until the project lead decides otherwise: row PL-9 of `docs/decisions-for-review.md` lists it with the other choices left to a person, and each later phase's design says so in its own "How this phase is built". D127 amends D68 for phase 5, as D70 did for phase 4; `CLAUDE.md`'s "How a phase is run" step 2 says both (the coordinator's edit of Nov 22, made before P0 starts).

## 3. The design in one page
1. **Every setting is a preset: a head row plus append-only versions with a JSON body.** One pair of tables holds eight kinds (phase 10 adds a ninth). One shape means one set of rules, one route file and one portal pattern, repeated. Note types keep phase 4's table and gain a head of the same shape.
2. **Presets are written only online, in the portal, never through the change protocol.** Admins work on desktop (`main.md:185`), so no phone can hold a refused preset change. Every write asks for a recent sign-in (`main.md:600`) and a reason, takes the team write lock first, and takes its revision from one function.
3. **A phone gets presets from one read route, by revision, after every sync, and keeps them in its team database with the team's other server copies.** They go with those copies at every sign-out. Everything works offline from that copy.
4. **Nothing is deleted. Remove means archive.** Old notes, orders and reports can always resolve an id. This is stricter than the PRD, which archives only what was used (`main.md:387`). Archiving a flag never takes it off a patient.
5. **What a count, a rank or a reader means never changes after creation**: an item's unit, a category's behaviour, a flag's tier and whether it is sensitive. To change one, archive and add. A platform update never changes one either.
6. **Records made against an older version are kept, never refused.** A record stores the preset id and the version it was made on. A phone offline cannot know about an edit or an archive.
7. **A platform update touches only copies the team never edited.** An edited copy gets an offer the admin may take. An archived copy stays archived.
8. **Note types are edited by a fixed list of operations, applied by one pure function on the server.** The server never accepts a definition built by a browser. No operation writes a mark that phase 4's rules read (who may read, what is required, what is Medical). Every stored definition names its own row's key and version, and passes phase 4's validator and version rules before it is stored.
9. **A patient's flags are changes made once; the current flags are worked out from them.** Two phones offline cannot conflict, and "who set it and why" (`main.md:320`) is the record itself. A clear takes off only the flag it names. A change's time is never later than when the server received it. A change made on the wrong patient is marked entered in error, once. No flag change is refused for something its sender cannot fix (D59).
10. **One rule says who may see a sensitive flag**, in `read-rules.ts`, and every read and every act calls it: the sync read, the review queue, the value sent back, the chart, the team index, search, the flag routes and the portal's flag list.
11. **No new permission keys.** Writing presets needs `team.manage_presets`. Flagging a patient needs `patients.edit`. Seeing a sensitive flag needs what a sensitive problem needs.

`team_preset_state`: `team_id uuid primary key` (FK `teams`), `revision bigint not null default 0`, `epoch uuid not null default gen_random_uuid()`. 0023 inserts a row for every existing team; a team made later gets its row at its first write.

**One function takes a revision**: `takeRevision(sql, teamId)` in `packages/forms/src/revision.ts`, beside `lockTeam(sql, teamId)`, the lock alone, which the installers take before they plan again (5.2). Both are in the forms package because the note type installer there calls them, and forms never imports presets (5.2). `lockTeam` runs the exact statement of `lockTeamWrites` (a package cannot import the API, section 2). `takeRevision` calls it, then steps the revision and records the step in one statement, so no take is without its record and the edge pays no round trip more for it:

```sql
with taken as (
  insert into sineobex.team_preset_state (team_id, revision) values (<teamId>, 1)
  on conflict (team_id) do update set revision = sineobex.team_preset_state.revision + 1
  returning team_id, revision)
select revision, set_config('app.revision_' || replace(team_id::text, '-', ''), revision::text, true)
from taken
```

The record is a setting local to the transaction, one for each team (a setting's name is identifiers only, hence the id without its dashes). It goes at commit, and with a savepoint rolled back, as the step does, so it never reaches the next transaction on a pooled connection. Every writer takes once and stamps every head it writes with the answer, before another writer in the same transaction takes again (team creation runs both installers in one): the admin routes, the note type publish, both installers and the seed. None writes the revision or the record itself: `db/test/preset-revision.test.ts` fails when any file but `revision.ts` and 0023 names `app.revision_`. A route also takes `lockTeamWrites` as its first statement, for one lock order (D32); the second take is free, since advisory locks are re-entrant. With the lock held to commit, revisions commit in order with no gaps, which is what the phone's pull relies on (6.1). `db/test/preset-revision.test.ts` holds both statements to `append_audit`'s key.

**The API begins every transaction read committed** (`createDatabase` in `services/api/src/db/database.ts`), whatever the database or its role defaults to. The lock-first rule and the installers' plan-again (5.2) rest on each statement seeing what committed before it began: a writer decides on what it reads under the lock, and a second plan sees what another writer committed while it waited. At repeatable read a transaction's snapshot is its first statement's, the scope's own settings, taken before the lock, so what it read "under the lock" would not be, and the second of two writers would fail with a serialization error instead of its refusal. `services/api/test/presets-revision.test.ts` holds it with the API's role set to default to repeatable read. The seed's transactions set no level of their own.

`epoch` is renewed after a database restore (a step of the restore procedure, which phase 12 writes; until then the step is `update sineobex.team_preset_state set epoch = gen_random_uuid()`, written into `docs/setup.md` by P0-migration), so a phone whose copy came from before the restore replaces it (6.1).

Security block for the four and for `note_types` (4.3): the team policy of `0004_sync.sql:185-195`; `revoke delete` on all five; `revoke update` and the `forbid_mutation` trigger on `team_preset_versions` and `team_preset_events`. The revision is held in the database too, as the second line under `takeRevision`: a team's revision never goes back, for the owner as well; the app role may update a state row's `revision` and nothing else (the epoch is renewed as the owner); and a head of `team_presets` or `note_types` is refused unless its `revision` is both its team's latest take in its own transaction, as `takeRevision` recorded it, and the team's current revision (the AFTER row triggers `team_presets_revision_taken` and `note_types_revision_taken`, both running `sineobex.keep_head_at_team_revision`, refuse with 23514 and the trigger's name as the constraint). That holds for every statement that writes a head: an insert, an update of any column, the update of an upsert, and an update that changes nothing (`set state = state`); an `on conflict do nothing` that finds its row writes none and is not checked. A take undone with its savepoint is gone, so the writer takes again; a second take in one transaction moves the record, and the heads written after it carry the second. So every head is written at a revision taken for it, and no pull can miss it (6.1): a route that forgets `takeRevision` is refused even when the head it touches already sits at the team's revision. The guard catches a writer that forgot to take, not one that fakes the record with `set_config`, which is why nothing else may set it. It holds for the owner too: a later migration that writes heads passes on an empty database and is refused on a real one, so it must take a revision for each team as `takeRevision` does, and be added to the scan's list. No take answers 0, so revision 0 on a note type head is 0023's fill only. Beyond these, 0023 holds: a preset keeps its kind; a preset head is at revision 1 or above; a platform version has no author; an event names one subject; and an event carries a reason exactly when a person acted, while the installer's acts (`installed`, `platform_updated`) are the only ones with neither.

### 4.3 Note types
Phase 4 owns `note_type_versions` (forms 3.1) and this phase changes none of its columns. A team's edit, and a team's copy, is a new row with `origin = 'team'` and `preset_version` null. A platform version installed or taken is a row with `origin = 'preset'` and `preset_version` the platform's number (5.2).

**Every stored definition names its own row** (D79, review finding NOT-8: `definitionFor` refuses any other, and the phone's store refuses a definition that names another key or version). Before the hash is taken, the definition's `key` and `version` are set to the row's: an edit sets `version` to the next version; a copy sets `key` to the new key and `version` to 1; a platform version installed or taken as the team's version N has its `version` rewritten to N. Where N is not the platform's own number, the hash is not the bundled preset's, so the phone downloads that definition rather than reading the bundle (`definition_store.dart` reads the bundle by hash). `hash = sha256Hex(canonicalJson(definition))`. Every row any path of this phase writes is read back through `definitionFor` in its tests.

`0023_team_presets.sql` adds the head phase 4 left to this phase: `note_types (team_id, key, title, state, current_version, platform_latest, customized, revision, updated_by, updated_at)`, primary key `(team_id, key)`. 0023 fills it from the versions present: `title` from the newest definition, `platform_latest` from the newest `preset` row's `preset_version`, `customized` true where any version of the key is the team's own (`origin = 'team'`; phase 4 wrote none, so it is false everywhere today, and a key holding a team version is never one a platform version may overtake), and the key standing in for a title where a stored definition has none, so no stored row can stop a migration that can never be edited. From then on the note type installer upserts the head of every key it installs or updates, and inserts the head of any key the team holds without one. A missing head is a write like any other (4.2): the plan finds such keys before the lock and again under `lockTeam`, and the run's one `takeRevision`, taken only when the run will write a version or a head, stamps every head it inserts or upserts. A run with nothing to write takes neither the lock nor a revision, since the installer runs at every list and pull. "Nothing to write" counts the missing heads: a team made after 0023 lands and before P4-install changes the installer gets versions and no heads, and once every key is `skip` nothing else would write them. Phase 4's every-run `insert … on conflict do nothing`, with no take, would be refused at every sync and the heads would never land. `title` is a copy of the definition's `title`. The head shares `team_preset_state.revision`; its acts are rows of `team_preset_events` with `note_type_key`. A key the team makes is `t_` and 12 hex characters, made by the server; it fits 0017's key pattern and the contract's. `0025_note_type_origin.sql` gives the head `origin_key`, the platform note type the head came from, unique per team, as `team_presets.origin_key` is: its own key for a platform note type an installer wrote, the old key's for an update taken as a new one, which the old one gives up; null for the team's own. 0025 filled it from what is stored, a `t_` key taken as new from its take's audit event (`note_type.platform_update_taken`, `replaces`), the only record of the key it replaced; a `t_` key with none, as one the team made, has no origin.

Rules the schema cannot hold are in `validatePreset` (5.3):

- An item's category exists. `result` is set exactly when the category's behaviour is `lab`. `medical` is true when the behaviour is `medication` or `lab`, so the switch is free only in a `supply` category (section 11, row 15).
- A bundle holding a `medication` item is `medical` (`main.md:447`), checked on the bundle's own write and whenever an item it names moves: only a move into or out of a lab category is fixed, so an item may move between a supply and a medication category under a bundle that holds it. A bundle's restore that would bring back such a bundle is refused 422 `invalid` with `[{path: 'medical', code: 'bundle_not_medical'}]`; a restore's other problems still refuse nothing (5.1). So an archived Non-Medical bundle whose item has become a medication cannot be restored while the item is one, and an edit refuses an archived preset (`archived`): the admin adds a Medical bundle instead.
- A `primary` flag is never `sensitive`.
- A field map's path names, in the note type's current version, what `fieldAt` (forms 7.1) points at as a field or as a grid cell (`<grid>.<row code>`, or `<grid>.<row code>.<child>` for a group cell), of kind `choice`, `number` or `flag`; with `{answered: true}`, also `text`, `date` or `duration`. A row code of a grid whose rows are picked is an option of the picking field. `equals` and `includes` name a code the field holds. `fromPath` names a number in the same entry, or the same row.
- **`sensitive_path`**: a field map is refused when what it fires on (its path with its `when`, and each `fromPath`; for a map with no path, its note type) lies anywhere `visibleAnswers` may take out from a reader who may read the note: a section marked `sensitiveExam` or `treatmentRecord`; a grid row marked `sensitiveExam`, or picked by a marked option; a region field holding a marked region; on a field holding an option marked `sensitiveExam` (`general_primary_care`'s `exam.systems` holds `gu`, `breast` and `rectal`), a `when` that is `answered`, `equals` or `includes` of a marked code, or any `equals` on a choose-many, since `sensitive-exams.ts` takes out only the marked codes, and the whole answer when nothing else is left (`includes` of an unmarked code, such as `skin`, is allowed, and so is `equals` of one on a choose-one, which every reader reads alike); a section that holds a diagnosis (a `problem` field), as forms 2.2's condition rule reads it; or a note type whose `sensitivity` is `sensitive`, refused as a whole. The note-level Medical gate is not `sensitive_path`'s: `visibleAnswers` answers null for a Medical-only type to a reader who does not read Medical notes, and every standard role with `inventory.view` or `billing.view_codes` reads them (`0002_identity_access.sql:87-97`). The CHW preset (`main.md:204`) does not, yet phase 6 shows it the orders of Non-Medical items, and 15 of the platform's 25 maps sit on Medical-only note types and suggest Non-Medical items (dressings, a wound's supplies). So phase 6 reads a line a mapping suggested as the note it fired on is read, whatever its item (phase 6 design, `orderVisibleTo`; BM-77), so a Medical-only type is not hidden for this rule. One function decides it, `mayBeHidden(definition, path, when)` in the forms package beside `visibleAnswers` (`packages/forms/src/interp/may-be-hidden.ts`; with no path, for the whole note type), and a test holds the two together: on every released note type that is not sensitive, for every reader of forms 7.1 for whom `visibleAnswers` is not null, whatever it takes out lies where `mayBeHidden` answers true. `preset-validate.json` holds `includes: 'skin'` on `exam.systems` accepted, and `includes: 'gu'`, `equals: 'gu'` and `answered` on it refused. A supply line is read by people with `inventory.view` and `billing.view_codes`, and would tell them what was found (D77's reason). The PRD's naloxone example is in the harm reduction note type, which is sensitive, so it cannot be mapped (12.2).
- A condition map may name codes on phase 3's sensitive list. Phases 6 and 7 count such a code only for a reader who may see sensitive problems.
- Every id names a preset of the same team and of the right kind; on create, edit and restore, none is archived (`reference_archived`). One `settings` row.

## 5. Rules
### 5.1 States of a preset and of a note type
An archived preset is never offered for new work. It stays readable everywhere, with its name. Every act a person makes carries a reason of 3 to 300 characters, kept in `team_preset_events` (4.2).

| Act | From | To | Who | Refused when (code) |
|---|---|---|---|---|
| Create | none | `active`, version 1 | `team.manage_presets` | body invalid (`invalid`); name in use (`name_taken`); it points at an archived preset (`reference_archived`) |
| Edit | `active` | `active`, version + 1, `customized` | same | `invalid`; `name_taken`; `reference_archived`; a fixed field changed (`fixed_field`); base version is not current (`stale`); body unchanged (`no_change`); for an item, after those, an active Non-Medical bundle naming it would hold a medication (`bundle_not_medical`, 4.4) |
| Remove | `active` | `archived`, `customized` | same | an active preset points at it (`referenced`, with counts by kind); `stale`; it is the `settings` row (`not_removable`). A flag patients carry is archived all the same and stays on them (below) |
| Restore | `archived` | `active` at the version it is at, `customized` | same | it is not archived (`not_archived`); `name_taken`; `reference_archived`; for a bundle, after those, it would come back Non-Medical holding a medication (`bundle_not_medical`, 4.4); for a field supply map, it would fire on, or count from, an answer only some readers of the note may see (`sensitive_path`, BM-77: a note type version taken in place while the map was removed may have hidden it). Nothing else `validatePreset` finds refuses a restore: a map whose note type changed since comes back, and fires on nothing |
| Take the platform update | `active`, update on offer | version + 1 with the platform body, and the head's name the body's; `customized = false`, `origin_version` the platform version taken | same | it is archived (`archived`); base version is not current, or another platform version than the one sent is on offer, or the copy is not in the state the update was reviewed in (`stale`, below); no update on offer (`no_update`); the update changes a fixed field (`fixed_field`: take it as a new preset); its name is in use (`name_taken`); it points at an archived preset (`reference_archived`); after those, the team's presets refuse its body for anything else (`invalid`), and for an item, `bundle_not_medical` as for an edit |
| Take the platform update as a new preset | `active` or `archived`, update on offer | the old one `archived` if it was active, and no longer the platform's (`origin_key` null); a new preset, version 1, with the platform body and the `origin_key` | same | it is the `settings` row (`not_removable`); `stale`, as in place; `no_update`; `referenced`, when the old one is active and an active preset points at it; `name_taken`, counted without the old one; `reference_archived`; after those, `invalid`, as in place |
| Reorder a tier's flags | `active` flags | each flag whose rank changes gets version + 1 and `customized`, so a later platform version of it is offered and never overwrites the team's order | same | the flags sent are not exactly the tier's active flags (`ids_mismatch`); a flag of the tier is not at the version sent (`stale`), whether or not the order moves it; a flag is archived (`archived`, which `ids_mismatch` answers first) |
| Platform install or update | see 5.2 | | the installer, no user | never refuses; it skips |

`presetWriteEffect` takes the preset's `kind`, so the `settings` row is `not_removable`. It tries each act's refusals in a fixed order, and the first that holds is the answer (`preset-rules.json` pins the order); its reorder row is `[archived, stale]`, each flag of the tier read with the version sent. A version a person takes from the platform, in place or as a new preset, is written as the platform's: `source = 'platform'` with no author, as 0023 requires; the event names the person and their reason.

**Only the platform version the person reviewed is taken.** Every row of the admin list carries the update on offer (`update`, 7): its platform version, its body naming the team's presets as taking it would write them, and the fixed fields it would change. A take sends that platform version back, and under the team lock any other version on offer is `stale`, as a newer copy is: any phone's pull runs the installer (5.2), which may offer a newer version between the review and the take without moving the copy's own version. The stale answer names the version on offer now, so the person reviews it before taking it. Nor from another state: every row carries its `state`, and a take sends it back as `baseState`. A Remove and a Restore keep the version, and a take as new archives an active copy, so a take sent from a removed copy's offer after another admin restored it would remove it again, and one reviewed on an active copy removed since would add what they removed; either is `stale` (in place, a copy removed since is `archived` first), and the answer names the state now, which the portal says as the Restore or Remove that moved it (PresetNotice). Taking an update in place on a flag the team ranked gives the flag the platform's rank back, since the platform's body replaces the team's, so two flags of a tier may then share a rank, and are ordered by name (5.3); the review shows that change (8.1).

**An archived flag stays on every patient who carries it.** Archiving is never refused for that, and never takes the flag off anyone: `currentFlags` keeps it (5.3), and every screen shows it with its name and "No longer on the team’s list". It can be cleared, and is never offered to be set again: the portal refuses a set (7), and a set sent by a phone that was offline is accepted (6.2), as every record made against an older state is (point 6).

### 5.2 A platform update (`main.md:387`, `:439`)
`platformUpdateEffect({exists, state, customized, originVersion, platformVersion, changesFixed})` returns one of:

| Case | Result |
|---|---|
| The team has no row with this `origin_key` | `install`: head plus version 1, `source = 'platform'` |
| Row exists, `platformVersion <= originVersion` | `skip` |
| Row is `active`, not customized, the platform is newer, and the new body changes no fixed field | `update`: version + 1, `source = 'platform'`, `origin_version` moves |
| Row is customized or archived, or the new body changes a fixed field, and the platform is newer | `offer`: only `platform_latest` moves. The body is untouched |

It lives in `packages/forms/src/platform-effect.ts`. `@sineobex/presets` imports `@sineobex/forms` (for `fieldAt` and `visibleAnswers`), so forms never imports presets; both installers call this one function, and `lockTeam` and `takeRevision` beside it (4.2), and both packages' tests read `platform-update.json`.

The preset installer is `installTeamPresets(sql: InstallSql, teamId)` in `packages/presets/src/install.ts`: a package, because the seed calls it, and one that imports no database library, as phase 4's installer. It runs where phase 4's `installPresets` runs (section 2.2): when a team is created, in the seed for both seeded teams, and at the start of `GET /v1/presets`, so a team gets a platform update the first time a phone asks. It works out its plan from the heads. With nothing to write it returns. If it would write, it takes the team's write lock (`lockTeam`, 4.2), works the plan out again under the lock (a second pull that read "no row" now sees the first one's rows and writes nothing), takes one revision for all of it (`takeRevision`, 4.2), writes each head with `on conflict do nothing returning id` and throws if one does not come back (only a writer that skipped the team lock can take it first, and the entries naming it would point at nothing), then each version and its `team_preset_events` row (act `installed` or `platform_updated`, the version it made, no reason or author, 4.2; an offer writes none), and answers its counts. A team that is up to date costs the pull one read of its heads. It writes no audit event: the caller audits `preset.platform_installed` in the same transaction. An entry it cannot write is skipped and counted: a body `validatePreset` refuses against the team's presets, such as a bundle whose item the team archived; a name another active preset of its kind holds, compared as the database folds names (`lower()`, which JavaScript cannot repeat for every script); a held copy of another kind; a copy whose current version cannot be read (`version_missing`); or an item update that would leave an active Non-Medical bundle naming the item holding a medication (`bundlesLeftNotMedical`, 4.4), with problem `{path: 'categoryId', code: 'bundle_not_medical'}`. That update is taken at a later run, once no Non-Medical bundle names the item: the file puts a bundle after the items it names, so the item is checked against the bundles as the team holds them, and a bundle the platform tags Medical in the same run lets the item move at the next. It and the route logs the count, as `forms.preset_differs` is logged, never a key: the log's allowlist has none, and a throw would fail every phone's pull. Platform data is `packages/presets/data/platform.json` (4.6), checked in CI by `packages/presets/test/platform-data.test.ts`: every entry passes its schema and `validatePreset`, every `originKey` it names exists, names are unique per kind, and a new `platformVersion` that changes a fixed field is reported, since every team will get it as an offer.

Note types follow the same table through phase 4's `installPresets`, which card P4-install changes. For each platform key it calls `platformUpdateEffect` on the head that names the key as its origin, else on the key's own, with `exists` whether a head names the key or the team holds any version of the key it is decided on, its own included (none: `install`), `originVersion` the newest `origin = 'preset'` row's `preset_version` of that head's key (none: null, so a key the team holds only as its own is offered, never installed over), and `state` and `customized` from that head; a fixed field here is `kinds`, `group`, `sensitivity`, `quick` or `auto`. `install` and `update` write that head's next version (1 for a new key, else one more than the newest row) with `origin = 'preset'`, `preset_version` the platform's number, and the definition's `key` and `version` rewritten to the row's (4.3). `offer` moves only `note_types.platform_latest`. Each install and update writes a `team_preset_events` row with `note_type_key`, act `installed` or `platform_updated`, the version it made and no reason or author (4.2); an offer writes none, since `platform_latest` shows it. A key the team holds without a head gets one, a write stamped with the run's take (4.3). `PresetDiffers` is raised only for an `origin = 'preset'` row with the platform's `preset_version` whose definition, with its `version` set back to the row's `preset_version`, does not hash to the platform's. A team's own version can then never be overtaken by a platform one (`main.md:387`): forms 3.2's rule ("skips a key whose newest row has `origin = 'team'`") with the archived case added. An install that may write takes the team lock first (`lockTeam`, the statement of `lockTeamWrites`), since a publish writes the next version too and the two would collide on 0017's primary key: it works out its plan, missing heads included, then locks and works it out again, as above, and stamps every head it inserts or upserts with one `takeRevision`, taken only when there is something to write. Its callers keep auditing `forms.presets_installed`.

**As built (P4, Nov 25).** `planNoteTypes` (`packages/forms/src/install.ts`) decides each key. It reads `exists` as "the team holds any version of the key", so a key the team holds only as its own is offered, never installed over; no real key is both, since a team's keys are `t_` keys. `changesFixed` compares the platform version last taken with the newest, `kinds` as a set. A version under which an active field supply map of the team would fire, or count its quantity, on an answer `visibleAnswers` may take out (`mapsExposedBy`, the test of `sensitive_path`) is offered, never taken in place, until that map is removed (BM-77); a take in place of such a version is refused 409 `sensitive_path` (7). The versions are written before the revision is taken, still under the lock, so a writer that skipped the lock is found before anything else is written. Team creation and the seed run two installers, each with a revision of its own (4.2), so a new team stands at revision 2. A run that writes anything (a version, an offer or a missing head) takes one revision and is audited: its result names what it installed, offered and gave a head (`installed`, `offered`, `heads`), and its callers audit `forms.presets_installed` with them whenever `installWrote` says it wrote, as the preset installer's offers are audited. A platform version taken as a new note type takes the platform's later versions on the new key, in place or as an offer by the same table, and the key it replaced is offered nothing.

`currentFlags`:
- A change marked entered in error is left out. So is a change whose flag is not among the team's flags, and one whose flag `hidden` hides from this reader.
- Changes are ordered by `effectiveAt` (4.5), then `id`.
- **Primary**: the primary-tier changes are folded in that order. A `set` makes its flag the primary. A `clear` makes the primary none only when its flag is the primary at that point; otherwise it changes nothing. So a clear of Yellow from a phone that never saw Red set takes nothing off (`flag-current.json` holds that two-phone case).
- **Secondary**: a flag is carried when its own last change is `set`.

A map that names an archived item skips that line. Phase 6 calls it; phase 5 pins it.

### 5.4 Note type edits
`PUT` sends `{baseVersion, reason, ops}`. The server loads every row of the key, oldest first, applies each operation in order with `applyNoteTypeEdit` to the newest definition, and collects the renames the operations yield. It sets the result's `version` to the next version (4.3) and checks it with phase 4's `validate` (its note type lookup answering the team's newest version of each other key), `versionProblems(every earlier version, next, {renames})` and `MAX_DEFINITION_BYTES` (256 KiB). It stores no renames: the resolved definition leaves them out of its hash (forms 2.6). It inserts the result as the next version with `origin = 'team'`. A released row is never changed. `rename_label` and `rename_option` yield one rename each; any other label change is refused by the version rules (`versions.label_changed`). The JSON Schema check cannot run in the API's edge bundle (section 2.2), so `applyNoteTypeEdit` builds only shapes the schema takes: `packages/forms/test/edit.test.ts` runs `checkFile` from `@sineobex/forms/schema` on every result in `note-type-edit.json`, and a phone test reads every result with `NoteTypeDef.fromJson`, since the phone refuses a whole list that names a version it cannot read (D84).

| Operation | Refused when |
|---|---|
| `rename_type {title}` | empty or over 80 characters (`title_invalid`); a title another active note type of the team holds, as `lower()` folds it (409 `name_taken`, after the validator's checks) |
| `set_hidden {path, hidden}`: hidden leaves a section or field out of the new version; shown copies it back, unchanged, from the last version that had it | the target is protected (`protected`); another field's `showWhen` or `mapsTo` names it (`in_use`) |
| `rename_label {path, label}` | `protected` |

**Protected**, worked out from phase 4's marks (forms 2.2), since a definition has no `locked` mark: every part of a note type with `auto` (Red flags, disposition and follow-up, `main.md:409`); a field with `required` or `noNormal` (the red-flag question, sensitive-exam consent and chaperone, `main.md:415`); a section with `needs`; a field of kind `action`, `problem`, `photo` or `info`. One function in the forms package decides it, and every operation calls it. A copied section keeps its marks, so what they protect stays protected.

Five rules hold in every case, each pinned in `note-type-edit.json`:
1. **No operation writes a mark.** `sensitiveExam`, `treatmentRecord`, `needs`, `required`, `noNormal`, `showWhen`, `handoff`, `mapsTo` and an option's marks are copied as they are. A field added to a marked section is covered by the section's mark, because `visibleAnswers` reads the section (lifecycle 6.4).
2. **`kinds`, `group`, `sensitivity`, `quick` and `auto` never change after creation.** Medical is a property of the note through its type (D56), and a reader's rights follow `sensitivity`.
3. **An id or a code the server makes (`t_` and a number) is never reused in that note type**, hidden or retired ones included, and a copied section keeps the source's ids only where the target never used them, so a mapping or a report never reads a new meaning under an old key.
4. **A note is read on its own version** (forms 2.6), so what is hidden or retired stays readable in every note that has it.
5. **One master list per field** (`main.md:410`). The database holds resolved definitions, with no list to edit once. So an option operation on a field is also applied to every field of the team's note types that `mapsTo` it, and to the field it maps to; each note type changed gets its next version in the same transaction (section 11, row 17). An `auto` note type is never reached.

Add a note type: a copy of an existing one (a new key, version 1; its `kinds`, `group`, `sensitivity` and marks come with it; `auto` and `quick` types cannot be copied), or a blank one with a title, `kinds` (`medical`, `non_medical` or both: `main.md:952`) and a timeline group. A blank one starts with one section, Notes, holding one text field, Notes, since a definition has no empty lists (forms 2.2; section 11, row 36); the admin then adds or copies sections. A type is Medical exactly when `kinds` is `['medical']` (forms 2.2, D56). Remove and restore follow 5.1 on `note_types.state`, a reason each; a team's own unused note type is archived too (point 4); an active field map that names the type refuses its removal (`referenced`). The `auto` note type cannot be removed (`not_removable`): the server refuses to finish a Medical note without it (lifecycle 3.3). A platform update that changes a note type's fixed field is offered, never taken in place: the admin copies the platform's type instead.

**As built (P4, Nov 25).** What is protected, with the copy of marks, the made ids and the words every operation uses, is in `edit-protected.ts`; a part holding a protected field anywhere inside it, a grid's cell or a cell group's field included, cannot be hidden. A retire also takes out a blocked pair (`excludes`) that names the retired answer, since `excludes` decides no reader and no answer in a pair could otherwise be retired. A retire of an answer a section's or a field's condition asks for is refused `in_use`, and a number field whose range holds no value at its decimals is refused `invalid`, each at its operation's index. A field shape the schema refuses is `invalid` at its index, never built. The limits of row 39 count the made ids a copy from another of the team's types brings. Renames are worked out once per publish, against what each part last said in any earlier version. Show again is offered for any part a published version hid: the list's `hidden` holds each section, field and answer an earlier version had and the current one lacks, in the words of the newest version that had it, with `showAgain` where `set_hidden` with `hidden: false` copies it back (worked out by that operation). A publish reads every note type the team holds, removed ones too, each at its current version: a removed quick encounter still holds what it maps to in use, and an option operation that reaches it gives it its next version while it stays removed; a copy may come from a removed type of the team, as a create's `copyOf` may. A publish whose result differs only in its number is refused 422 `no_change`, as a preset edit is, and a publish holds at most 200 operations (`MAX_PUBLISH_OPS`), since each reads the version so far. A take in place keeps every version rule but the label rule: the platform's labels are its own meaning for its paths. A title with spaces around it is refused on create and in `rename_type`, as a preset's name is. A label, an answer's words or a section's title with white space before or after its words is refused at the request (422 `validation_failed` at its path), as a title is, never trimmed; the editor holds typed words without the spaces around them.

**The pull.** It answers `{reset, revision, epoch, presets: [{id, kind, state, version, originKey, body}]}`: every head whose `revision > since`, with `revision` the greatest revision among them, read in the same statement (`since` itself when none is sent back, and 0 on a reset with none). Every write takes the team lock before it takes a revision and holds it to commit (4.2), so once a revision is seen no lower one can commit later. A pull is a reset when `since` is left out, when `since` is above the team's revision, or when `epoch` is not the team's (a restored database, 4.2): the answer is `reset: true` with everything, and the phone replaces the table. A pull with no `since` is sent everything anyway, so a reset costs it nothing, and a phone that lost its revision but kept rows a restored server no longer has replaces them too. A `since` above the safe-integer range, which no team can have taken, is answered as one left out; `since` is a whole number of at most 19 digits and `epoch` a UUID, else 422 `validation_failed`. An answer is written only into the team database it was asked for, and only while that database is still the one the controller holds open, not frozen, for the same sign-in; any other answer is dropped, as phase 3's review (P3) made the index's downloads do.

|---|---|---|

A stale sign-in (`reauth_required`) is not logged (D98).

- A flag id names its flag to every member, through `GET /v1/presets`, and the audit chain cannot be redacted (D41); a reader of the audit log need not hold `patients.view_sensitive`. So a change of a sensitive flag is logged without its flag id, as phase 3's `problem.created` carries no code.
- Preset bodies and reasons are admin text, not patient data, but an admin can type anything. Audit details carry field names and counts only. A preset's reason lives only in `team_preset_events`. The portal warns under every free-text box (8.1).
- A flag change's reason, and an entered-in-error reason, is patient detail. It lives in `patient_flag_changes`, in `field_history` (`storeCreate` writes every created field there), in `quarantine_items` while a change is held, and in the phone's encrypted store. It is never in audit details, logs, notices, URLs or page titles, and an entered-in-error change's reasons are shown only to its author and Program Admins (6.2).
- A sensitive flag on a patient is a sensitive detail (`main.md:121`), hidden by the one flag rule (6.2) wherever it is read: the sync read, the review queue, which leaves a hidden flag's held change out (D145), a value sent back, the chart, the team index and search.
- Team setup, `GET /v1/presets`, `GET /v1/presets/flags` and the note type routes name no patient, so none writes a patient into the audit log (as phase 4's Home counts). The phone's `presets` table and its `presets.` keys hold no patient data and nothing derived from a legal name (D40). The installers log counts, never a preset's key.
- Platform and seed presets pass the PHI guard, which reads `packages/presets/` as a fixture tree as it reads `packages/forms/` (`tools/phi-guard-rules.mjs`); demo additions start "Demo:".
- A reason and a search by flag travel in POST bodies.
- The phone's flag list (8.2) is audited as `patient.searched` from the team index, naming the patients shown, each page of the list an entry of its own, with `criteria: []`: the phone's offline criteria name no flag, and none is logged (CO-14).

## 12. Risks and departures from the PRD
### 12.1 Risks
1. **Ids inside a JSON body have no foreign key.** Only the API checks them. `presets-refs.test.ts` walks every body, and `referenced` stops an archive from leaving a dangling id.
2. **This phase changes what phase 4 built.** P4-install changes `installPresets`, and P4-offered the note type list. Phase 4's own tests (`services/api/test/forms-routes.test.ts`, `db/test/install-presets.test.ts`, `packages/forms/test/install.test.ts`) run unchanged beside the new `install-update.test.ts`, and every row any path writes is read back through `definitionFor` (4.3).
3. **Body shapes will grow.** A new field must be optional with a default in both parsers. A phone skips a kind it does not know and ignores a field it does not know (pinned in `preset-bodies.json`). It refuses what the schemas refuse, so a body a server widened (a longer bound, a new colour, kind or result type) is skipped by a phone whose app does not read it yet: ship the phone's reader first. A copy written by another reader is pulled whole again, so the skipped presets come back once the phone updates; a widening the reader's enums do not show moves `presetsReaderRevision` (`models.dart`), and `models_test.dart` fails on a change to the vectors' cases until someone looks at it.
4. **A phone offline for days works from old presets.** By design (point 6). Team setup shows when the copy was last updated.
5. **The fake can drift from the API** (plan risk 7). Every row of 6.2 and every mirror of 6.3 is a parity case.
6. **A custom role may lack what the PRD implies.** A sensitive flag follows the sensitive-problem rule (section 11, row 29), so a custom role with `patients.view_sensitive` but neither `encounters.chart` nor `billing.view_codes` does not see it. Every standard role that holds the key does (`0002_identity_access.sql:87-97`).
7. **An admin can type a patient’s name into criteria, a bag name or a reason.** The hint is the only guard; audit details never carry the text, and presets stay in the phone's encrypted database.
8. **One option edit can publish several note types at once** (5.4, rule 5). One transaction, one audit event per type, one revision step.
9. **A team's edit is the one place a definition is not checked against the specification by machine** (D64). The fixed operations, the protected parts and phase 4's validator and version rules are the defence; the edit vectors hold one case per mark.
10. **A database restore can leave phones with a copy mixed from two histories** unless the epoch is renewed (4.2). Phase 12's restore procedure must renew it; until then the step is one statement, in `docs/setup.md` (P0-migration).
11. **Supplies given in a sensitive note type are never suggested.** Harm reduction, psychological and sexual and reproductive health are sensitive types, so no map may fire on them (`sensitive_path`), the PRD's naloxone example included. What is given there is entered by hand or through a bundle in phase 6.
12. **Presets go with the team's server copies at every sign-out.** A team first opened offline afterwards offers no flags, no Team setup and no risk level at intake until it is opened online (6.1; section 11, row 34).
13. **The admin note type list reads and checks every version of each note type at each read** (for `hidden`, 7). A team with a long edit history reads every stored version at each list, and pays a hash for each beyond what the definitions cache holds (`MAX_DEFINITIONS`, 64). If it proves slow, keep `hiddenParts` per key and current version, which is exact, since a version never changes. The whole-phase review kept it as this risk: the list is admin-only, and nothing a phone pulls depends on it (sync, settled 4).
14. **A section the team made in one of its note types can't be copied into another that made parts too.** Each note type numbers the parts the team makes in it (`madeIds`), and rule 3 refuses a number the target ever used. The editor names the part and the way on, "Undo this copy, then add a section of your own with the fields you need."; a section the team made holds no marks (D134), so one rebuilt by hand reads the same to every reader and only its typing is lost. The whole-phase review kept it as this risk (accessibility, settled 2): renumbering would change 5.4's copy, unchanged with its fields, answers and marks, and every path a `mapsTo`, a question or a field supply map names inside it.
15. **A flag change still being stored when the team index is worked out can read as held by it** (D141, D142). A receipt dates a change by its push's transaction, which can wait on the team's write lock. Since the phone starts no refresher while its own push is under way, what is left is a push whose answer is lost (a timeout) while its transaction still waits on the lock, then an index downloaded before that transaction commits: the index is worked out after the receipt's time and leaves the change out. The phone then shows the index's word without its change until the next index or chart. It never shows its own change over a teammate's later one. The exact remedy is D142's counter: the receipt carries the team index version its change's bump set (0024's trigger moves it in the push's transaction), the phone counts its change after the index's word while the index's version is below that, and the test server's index version, worked out from its content today (`putIfAbsent(content)`) and so able to go back to an older number, becomes a counter that only goes up. Not repeatable read for the index: its own audit append takes the team's write lock and reads the chain, which needs read committed.
16. **A second mark held after a first was not applied says nothing** (review finding S4). The phone reads `/v1/me` only at sign-in (`session_controller.dart`, `verifyCode`), so a role lowered at the desk leaves its cached permissions in place for the session, and the author's Entered in error mark is held, which is right. If a Program Admin rejects it, the notice says so; but the server tells a sender once per change (`flagChangeNotApplied`), so a second mark held after that shows no "Sent for review", and Entered in error is offered again; once one is accepted, the next chart shows the change marked. The fix is one `flag_change_not_applied` notice per held change, naming its change ID, so the phone settles the mark it names: a migration, the API, the contract, the test server and the phone, for a case that needs a role lowered mid-shift and two marks in a row. W1's mark sentence tells the person of the first.
17. **After a merge the phone learns of from the team index, a held create a Program Admin took shows "Sent for review" on the survivor until a chart of the survivor lists it.** The flags view and the notice read the survivor's chart only, though the merged patient's chart the phone still holds lists the change, so a held mark's notice of that change names no act there. A whole chart of any patient of the group could count instead.
18. **A held or accepted answer whose hash never matches is sent again for good, and shows nothing in Needs attention** (D147). It confirms nothing and waits for its stored receipt, which a server holding another value under the change's ID never gives, so the change is sent again after each backoff, the batch's other changes answered each time. That is a server fault; the devices page shows the phone's waiting work.
19. **The test server dates notices by one clock reading per push.** Each change of a push has its own receipt instant there (6.3), as the API's transaction per change dates it, but the notices the API inserts in those transactions do not. No test reads one notice's time against another's.

### 12.2 Departures and readings
- "Archived rather than deleted" applies to used note types (`main.md:387`); this design archives everything (point 4). "Edit" a note type is read as the operations of 5.4, not a free form builder. A protected part stays (`main.md:409`, `:415`, `:945`). Phase 4 lets a new platform version remove anything (forms 2.6); a team's edit may remove less.
- "Remove" a bundle (`main.md:128`) is refused while a mapping or another preset points at it; the admin removes those first.
- Bags are defined here though shared bags are phase 6 (`build-plan.md:95`), because bag minimums need a bag to hang on.
- The patient record's "priority flag" (`main.md:234`) is worked out from flag changes, so there is no value two phones could overwrite, and `patients.priority_flag_key` (`0009_patients.sql:58`) stays unused. 0024 says so in a column comment (4.5); 0009's line comment stays as merged, since a merged migration is never edited.
- Setting flags on a patient is stage 11 (`main.md:777`), which the build plan puts in phase 9 (`build-plan.md:113`). It moves here because phase 7 ranks patients by both tiers (`build-plan.md:102`), and a flag nobody can set is shown to no one. Phase 9 keeps the continuity queue.
- Mappings fire "on the action field" (`main.md:431`). The app cannot tell which field that is, so it is guidance on the page plus the platform's own choices (4.6).
- "Each one lists the sections the phone form shows (vitals, wound, support, needs, interaction)" (`main.md:945`): a team type copies a section only from a type of its own kinds, group, sensitivity, quick and auto (5.4), so one type cannot combine sections from different platform types, such as vitals (`general_primary_care`, clinical) and a wound section (`wound_care`, wound). An admin adds fields and sections of their own beside the copied ones (section 11, row 20).
- "Every template field can be tied to an inventory preset" (`main.md:424`): a field in a part only some readers may see, or in a sensitive note type, cannot be (`sensitive_path`, 4.4), the PRD's own naloxone example among them (12.1, risk 11).
- "Social needs tapped (food, hygiene) → the matching kits" (`main.md:429`): a kit counts as one (`main.md:442`), so a kit a field suggests is an item, and a map line names an item, never a bundle.
- The PRD asks for a reason on items, bags and minimums (`main.md:930`, `:951`, `:955`); this design asks for one on every preset and note type write (section 11, row 10).
- The PRD's levels are named by their colours (`main.md:120`, `:316`), and its pills read "Red · High" (`main.md:945`, which wins until module 3 is rewritten, `main.md:926`). The platform's primary flags are named High, Medium and Low and coloured Red, Yellow and Green.
- An archived flag stays on the patients who carry it (5.1), where "remove" might be read as taking it off them.
- The PRD names no alert rules (`main.md:190`), so none are built (section 11, row 28).
- The team index holds no clinical content (D29), and the PRD's list of its fields has only the "priority flag" (`main.md:271`). Here each entry also carries the patient's secondary flags, a sensitive one such as Pregnancy only for a reader who may see it (`idx1+sens`, which phase 3 reserved), so both tiers filter offline (`main.md:316`). The narrower default would be the primary flag and the non-sensitive secondary flags only (section 11, row 38).
- "Logistics and admins search and filter by both" (`main.md:316`): on the phone the patient list filters by both tiers offline; in the portal a flag narrows a name or birth search, and a flag alone is refused, as phase 3 refuses a search that would browse the list (7; section 11, row 37).

### 13.4 The cards
Levels follow `docs/plan/README.md`. An always-X path is X: the API's `sync/` code, the phone's `lib/sync/`, the phone's test server, a migration with policies or triggers, `.github/` and `tools/`. So is a card whose wrong line would lose a write or show something to the wrong reader where no other card's test would catch it: the revision (4.2), where answers may be hidden (`mayBeHidden`, 4.4), what a note type edit may not touch (5.4). Each unit's tests card is X, since what it writes is what the T cards are held to, and so is the Done when's story. A screen or a page is R, and so are the contract cards, the seed and the tests that walk the Done when. A T card's tests are written first, by its unit's tests card. No row is S: none is left to a machine check alone. Levels say where review is strictest ("How this phase is built").

Short paths: `api/` is `services/api/src/`, `api-test/` is `services/api/test/`, `phone/` is `apps/mobile/lib/`, `phone-test/` is `apps/mobile/test/`, `forms/` is `packages/forms/`, `presets/` is `packages/presets/`, `vectors/` is `packages/contract/test-vectors/`, `(app)/` is `apps/portal/src/app/(app)/`, `portal/` is `(app)/team/presets/`, `parts/` is `apps/portal/src/components/presets/`, `actions/` is `apps/portal/src/app/actions/`, `e2e/` is `apps/portal/e2e/`. A file that does not exist yet is new; every other is edited.
