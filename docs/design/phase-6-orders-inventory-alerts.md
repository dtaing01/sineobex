## How this phase is built
By the frontier model with helper agents, from the card index of section 13, as phases 4 and 5 were (D127; the default of PL-9 in `docs/decisions-for-review.md`, which the project lead may still decide otherwise). What that means here:

- **The card list of section 13 is the work-list.** Each row's files, needs and order hold. No card is written in full, so there is no `docs/plan/phase-6-orders-inventory-alerts/` folder, and `tools/card-run.mjs` is not used. What only a small model needs (a card's length, how much it may read, at most three source files a card) does not apply; unit order, who owns each file and each rule, which units run side by side, and each row's needs do.
- **The order of 13.1 holds.** I0 is the first unit; I1 lands alone, in two parts, with CI green; at most two agents work at once (`CLAUDE.md`), each pair owning disjoint files but for the shared files 13.2 orders. A migration is pushed only after its review.
- **A unit is built from the design sections its rows point to**, tests first, by one agent in its own worktree (`CLAUDE.md`, "Running units with helper agents"). Each unit's commits are also pushed to `claude/p6-wip-<unit>`, which is never merged; the project lead deletes those branches when the phase lands.
- **What a card's checks gave is replaced.** Every rule is removed by a script to see its test fail. Each unit gets an independent review, each confirmed finding shown by a failing test before it is fixed. The whole-phase adversarial review at the end is I7-review.
- **Levels still say where review is strictest.** An X row gets the coordinator's second review.
- **Nothing is asked of a person mid-build.** Every default of section 11 is listed in `docs/decisions-for-review.md` under who decides, as "Chosen, not yet built (phase 6)", from this reviewed design and ahead of the build, and each card that builds one marks it `PLAN-OPEN (<row>):`. The close names the files its markers are in.

## 3. The design in one page
1. **A count is a sum, never a stored number a phone writes.** Every stock change is one immutable row with a signed quantity. Two phones offline cannot conflict, and −2 is plain arithmetic (PRD main 126). A count already held what an order given before it took, so a dispense dated before a count that arrives after it is absorbed by the server (5.2).
2. **Phones send orders; the server writes the stock movement.** One synced record type carries the order and its bag, so an order and its deduction cannot disagree, and the order is stored with its encounter. A held order moves no stock until it is accepted.
3. **The server never refuses an order for a judgment rule.** The item has already been handed over. A missed allergy or a credential that may not order is stored and flagged for review. A refusal is kept for what the worker can fix (D59), each with its fix (6.1); a rule that throws is a `definition_error`. An order is judged by the item version it names.
4. **Medical follows the item and the credential, as phase 4 made it follow the note** (D56), **and so does sensitivity.** A Medical item needs a credential that charts Medical; a medication also one that orders. An item marked sensitive is read as a sensitive note is, one marked treatment as a treatment record is. The visit's kind only decides what the phone offers.
5. **Items, bundles, mappings and bags are phase 5's presets.** This phase adds what a preset cannot hold: stock, a bag's owner, outings and orders, and three optional body fields. It stores preset ids and versions and defines none of them again.
6. **One read rule each, in `read-rules.ts`.** Who reads an order (`orderVisibleTo`) and a patient alert (`patientAlertShown`) is decided once and asked by the sync read, the review queue, a value sent back, the visit read, the chart, the supply log and the review list (D99).
7. **The allergy check is one pure function, run twice.** The phone runs it over the allergies the profile shows, this phone's own included; the server runs it again over what it holds. Vectors pin both.
8. **Stock alerts are rows opened and closed by where the balance stands** after each movement, in that movement's transaction: a kind opens when its line is under and none of that kind is open, and closes when its line no longer holds. Who is shown one is worked out when it is read, so a role change needs no repair.
9. **Nobody on a run is shown a stock alert, on any surface, and no phone shows a count.** The portal shows the team's alerts to `inventory.view`, and a phone and a push to the people who restock and to the route lead, each only once any outing they are on is over (PRD main 126). The order screen lists what a bag carries, not how many.
10. **"The route" is an outing until phase 7.** An outing is a day, a lead, up to three members and the bags taken. It gives this phase the route's bags, its lead and who is on the run without building routes. Phase 7 attaches a route to it.
11. **Counting is online only.** A count (a set-up count, a correction, or an item taken off a bag's list) is the one kind of stock change that is not a sum. The server works out its difference under the team lock, in the portal.
12. **Banners are computed from data the phone already holds**, plus one small synced record for the alerts staff write. No banner ever blocks.
13. **Push text comes from a fixed list of sentences.** The payload type has no free-text field, so a name cannot get in. The sender is an interface that sends nothing until the accounts exist and counsel answers.
14. **No new permission keys** (D37). Every check uses keys in `services/api/src/auth/permissions.ts`.

## 4. Data model
Five migrations, 0026 to 0030 if nothing lands between, all level X (policies and triggers). Each table has `team_id uuid not null references sineobex.teams (id)`, `created_at timestamptz not null default now()` and the team policy block of `0009_patients.sql` 478-490 (`team_id = sineobex.current_team_id() or sineobex.is_platform_scope()`, `using` and `with check`). IDs are `uuid`. Every foreign key to a team table is composite with `team_id`, a device's too (0026 adds the key that needs, 4.1), and every unique index starts with `team_id`, so no write is checked against a row the policy hides (a conflict there raises 42501 and stops the push: review finding DR13). An item, a bundle, a mapping or a bag is a composite foreign key to phase 5's `team_presets (team_id, id)`; the API checks the preset's `kind`, as phase 5 does for `flag_id`. Every query this phase writes names `team_id` in its own SQL, row-level security being the second line (D5, D146).

A record changed by one mark takes the shape of `patient_flag_changes` (0024 15-55), which built on `referrals`' (0021): `version`, `field_versions`, `field_meta`, `updated_at` with its touch trigger, `change_id` (the sync change that carried it), `approved_by` (the Program Admin who accepted it from review) and `received_at` (the server's receipt), the mark's why, who and when all three or none, a guard trigger as 0024's that lets only the mark and its bookkeeping change (class 23, naming its constraint), and `revoke delete`. An append-only table takes `forbid_mutation` and `revoke update, delete … from sineobex_app` (0009 495).

A guard trigger lets only `closed_*` change, once; `revoke delete`.

## 5. Rules
### 5.1 An order
| State | Reached by | Who | Offline |
|---|---|---|---|
| Suggested (phone memory only, never stored) | A bundle is applied (`bundleLines`), after its prompt (below), or a mapping fires on a note the person acts as the author of (`suggestSupplies` over the answers that count; phase 5 5.3) | The person charting | Yes |
| Ordered | Confirm on the supply screen, or one tap on a single item | `encounters.chart` (BM-88). A Medical item (`medical` true: every medication and test, phase 5 4.4) also needs a credential with `chartMedical`; an item in a `medication` category also `orderMedications` | Yes |
| Voided | "Remove", with a reason | The order's author; anyone else's void is held for a Program Admin (6.1; BM-94) | Yes |

There is no edit. A wrong quantity is a void and a new order. An order is accepted whatever state its encounter and notes are in, and it is outside every note's content hash, so it never changes what was signed (D57; BM-90).

**What the phone offers** (`itemOffered`, 5.3). A Medical item or bundle is listed only in a visit whose kind is Medical and that has a patient (lifecycle 3.10), to a credential with `chartMedical`. A medication is listed but disabled for a credential that may not order. On the platform's categories OTC and Rx are both medications, so a student or a CHW is offered OTC items disabled (BM-63). A CHW adding a Social needs note to a teammate's Medical visit is offered Non-Medical items only.

**Before an order is placed.** Tapping an item with a `result` asks for the result first (its options, or a number in its unit), and the order is placed with it (PRD main 104). Tapping an item that captures a lot asks for its lot and expiry, which may be left empty (BM-93). Applying a bundle whose `prompt` is not empty first shows the prompt on its own screen with **Continue** and **Back**, every time the bundle is applied, offline too; its lines are suggested only after Continue, and Back suggests nothing (PRD main 445; BM-74). Then the allergy check (5.4), before any line is ordered.

**Suggest, then confirm.** The supply screen (8.4) holds the suggested lines from the person's own notes and the bundles they applied. It opens from the summary's **Supplies** row, and Complete opens it first, once, when the visit holds suggestions the person neither confirmed nor dismissed: **Confirm supplies** and **Nothing given** both go on to Complete, and Back returns to the summary. It never stops Complete (PRD main 382, 424, 471; BM-99). Whether a visit's suggestions were seen is kept in memory, so after a restart Complete opens the screen once more.

**The Quick encounter.** When its Medication section's Order holds OTC or Prescription, the supply screen shows a line "Which medication was given?" that opens the Orders screen on the OTC or the Rx chip, the first the answer names. The order is placed there, through the allergy check, as any single item; Nothing given clears the line. No mapping is used: the section names no item (PRD main 404, 409; BM-100). Delivery yes/no stays phase 7's delivery task (PRD main 418).

**The bag.** `pickLocation` (5.3) picks it, among the bags the person carries today (8.1): the chosen outing's, then their own. Staff change it with the line's bag chip on the supply screen, or on a row of Given in this visit (8.5), where choosing another bag voids the order with the reason "Wrong bag", filled in, and places the same order at the chosen bag, in one local transaction (PRD main 475).

**What the server checks.** The credential only, never the visit's kind, which a teammate's switch to Medical may not have synced yet (D56). It flags, never refuses. `mayOrderItem` reads the item and its category's behaviour at the version the order names (`item_version`, as phase 5 6.4 accepts it), and the credential `signedUnder` finds for the order's time, its `notBefore` the encounter's receipt as an addendum's is: a time it does not believe reads the credential now (PL-30).

**Who reads an order** (`orderVisibleTo`, 5.3; one copy, in `services/api/src/sync/read-rules.ts`, asked by every read of section 6.1 and 7). Its author always. Anyone else, all of:
- for a line a mapping suggested, its note is one they may read (`fromNote.readable`: `visibleAnswers` gives them that note);
- a Non-Medical item with `patients.view`; a Medical item as a Medical note is read (`mayViewProblems`: `patients.view` with `encounters.chart` or `billing.view_codes`);
- a `sensitive` item also `patients.view_sensitive`, as a sensitive note type (all of which are Medical) is read, which is the sensitive projection a sensitive flag needs (PL-23);
- a `treatment` item also `patients.view_sensitive` and a credential that charts Medical, as a treatment record section is (CO-1).

The item's marks are read both at the order's version and as the team holds them now, and the stricter counts: Medical if either is, the higher sensitivity of the two. A line a bundle suggested is read, besides, by the strictest marks among the items its bundle's version lists, as the team holds them now, as a mapped line is read by its note: the order names its bundle, whose name every phone's presets hold, so the unmarked line of a team's bundle that also holds a sensitive item would otherwise tell its reader what the bundle was for (the platform's sensitive bundles hold one item each). So raising a mark hides past orders at once, and nothing lowered later shows an order to a reader it was hidden from (CO-19). A voided order's reason goes only to its author and a Program Admin (PL-19's: `team.manage_users`); anyone else reads it voided with no reason, the key left out as `flagChangeShown` leaves a mark's (PL-35). The sync read also needs `encounters.chart`, as a visit's records do (`readNeed`).

### 5.2 Stock
| Movement | Who | Where | Effect on the sum |
|---|---|---|---|
| `dispense` | Written by the server for each order | Sync | −quantity at the order's location (team stock when null), dated by the order's time |
| `void` | Written by the server when an order is voided | Sync | +quantity at the same location, dated by the void's time |
| `count_absorbed` | Written by the server after a late `dispense` or `void` (below) | Sync | The opposite of the movement it names |
| `restock_out` and `restock_in` | `inventory.manage` | Portal | −q at team stock, +q at the bag, one `pair_id`. From outside: `restock_in` alone (TM-38) |
| `received` | `inventory.manage` | Portal | +q at team stock |
| `setup_count` | `inventory.manage`: a count of kind `setup`, once per location | Portal | counted − current sum, 0 included, one row per line |
| `recount` (a correction) | `inventory.manage` and `team.manage_users`, PL-19's Program Admin (PRD main 961; Logistics records restocks but corrects no count: PL-31): a count of kind `correction`, with a reason | Portal | counted − current sum, 0 included, one row per line; an item added to a bag is a line of it |
| `not_carried` | As a correction, with a reason | Portal | −current sum, to 0; clears `carried`, so the bag no longer lists the item and its minimum no longer counts (PRD main 954). A later restock, receipt or count of the item lists it again |

**After every movement** the server reads, under the team lock, the balance after it, the bag's current minimum for the item (none while minimums are off or the bag does not carry the item) and the item's open alerts at the location; calls `alertEffect`; and opens or closes alert rows in the same transaction. A kind opens when its line is under and no alert of that kind is open, and closes when its line no longer holds: an alert follows where the balance stands, not only a crossing, so no movement meets the one-open index (4.2). An alert is never edited by a person. A minimum changed in the portal takes effect at the item's next movement ("after an encounter or a recount", PRD main 477): one raised above the balance opens a reminder then, and one lowered under it, or turned off, closes the reminder then. Until that movement a below-minimum alert is shown only while minimums are on, the bag carries the item and its current minimum is above its balance (5.6), so turning minimums off or lowering one quiets it at once; the row stays as history.

**A count taken while orders are unsynced.** Sums commute; a count does not. A count records when it was taken (its `effective_at`, the server's time). A `dispense` or `void` that arrives after a `setup_count`, `recount` or `not_carried` of its item at its location, and is dated before it, is stored as sent and followed in the same transaction by a `count_absorbed` movement of the opposite quantity naming it: the count already held what it took (`absorbs`, 5.3). `alertEffect` runs once, after both rows, on the balance they leave, which is the balance before them, so the pair opens or closes only what a minimum changed since the last movement calls for. Every line of a count is a row, a line that matched among them (4.2), so a late order is absorbed by any count of its item. The supply log shows both rows.

**Which outing a movement is on.** The server finds it, and takes the phone's word only to choose among the outings it found (`outingOf`, 5.3). For a bag, the outings whose bags include the location and whose window holds the movement's time: from the service date's UTC midnight to 36 hours after, or to the outing's end if it ended sooner (`outingOver` at that time, TM-37). For team stock, the outings the order's author is a member of whose window holds the order's time. Of those, the one the order names (`outingId`) when it is one of them, else the one with the earliest service date; with none, no outing. Two windows can hold one time: in US zones a run's evening is already inside the next day's window, so an order given at 20:00 in Detroit on today's run, from a bag that is also on tomorrow's, is on today's, and so are its alert and the lead it alerts. An order given during a run and synced after the run ended is still on it. An alert's outing is the outing of the movement that opened it.

**Recount due.** While the team's `recountDays` is set, a location whose last `setup_count` or `recount` row (a line that matched included) is older than it is due a recount: "Recount due" on the Inventory page, the location's page and the portal's Home count. Nothing blocks, and nothing reaches a phone (PRD main 475; BM-97).

Team stock has no minimum, so its only alert is `negative`; bags warn through their minimums (PRD main 473; BM-98).

### 5.4 The allergy hard stop
- **Match.** Normalize the item name, each of the item's `allergenTerms` and each active allergy's substance with the pinned name normalization (D43; `packages/contract/test-vectors/normalize.json`) and split into words. An allergy matches when a term (or the item name) and the substance are equal, or one is a run of whole words inside the other. A side shorter than 3 characters matches only when equal. Allergies marked entered in error never match. All categories are checked (BM-91).
- **When.** Before every order, single or in a bundle, whatever its category (PRD main 450: "Every order runs the allergy hard-stop check first"). A bundle with a matching line stops before any line is ordered.
- **On the phone.** `allergyMatches` reads the patient's `AllergyView` list, the one the profile's badge is drawn from (`apps/mobile/lib/patients/patient_repository.dart`): the group's allergy records the chart or the index entry lists, plus this phone's own, confirmed or not, less any marked entered in error, here or on the server. An off-route patient opened from the team index has its entry imported as records first (`importIndexEntry`), so the same list serves, and an allergy recorded at this visit offline stops the next matching order. `allergyOutcome` not `clear` → the hard stop (8.3).
- **Ways out.** Only **Record and give**, with a reason of 3 characters or more, places the order, storing `allergyOverride {allergyIds, reason}`. Every other way out places nothing and returns to the list, a bundle's other lines unordered too: **Choose something else**, the back gesture, Escape, a screen reader's dismiss, the store freezing and the app going to the background. **Choose something else** returns to the same category's list with the items that match the patient's allergies marked "Allergy", so another item is one tap; the app recommends no drug (Build plan 97; BM-92).
- **On the server.** The same two functions over the server's active allergies of the encounter's patient group, with the item's name and its current `allergenTerms`: a word added since the phone's copy is what the re-check is for. `clear` and `overridden`: stored. `unchecked` (the phone did not hold the allergy): stored with the flag `allergy_unchecked`, the receipt says so, the author gets a notice, audit `order.flagged`. An order that carries an override writes `order.allergy_override` (`allergyIds`, `reasonLength`) whatever the outcome, since a person overrode a stop with a reason ("a logged override", Build plan 97): one whose allergy was marked entered in error on the server since is `clear` and is still logged, and one with a match the phone did not hold is logged beside its `order.flagged`. Never refused (CO-17).
- **No patient, or allergies "not asked".** The check has nothing to match. No stop; the allergy badge, which stays on screen while ordering, says "Allergies not asked yet". A visit with no patient is offered no Medical item (5.1).

### 5.5 Passive banners and patient alerts
`chartBanners` returns, in this order: active `safety` alerts; active `clinical` alerts; a point-of-care result recorded in the last 7 days ("New test result"), from the chart answer's `labOrders` (the group's lab orders of those 7 days that `orderShown` gives the reader, 7) and, on the phone, its own, so the phone and the portal draw it from the same orders, not the phone from its last three visits alone; `other` alerts (BM-95). "Allergies not asked yet" is the badge's, not a banner's (`allergyBadge()`). The banner about being unable to consent (phase 3) stays where it is. A banner's words wrap, never truncate; the strip scrolls with the chart and never covers it.

A patient alert is read by `patients.view`, and one marked sensitive only by a reader with the sensitive projection (`patients.view_sensitive` with the problem list's keys, PL-23) or by its author: `patientAlertShown`, one copy in `read-rules.ts`, which the chart answer, the sync read, the records read, the review queue, a value sent back and the banners all ask. One the reader may not see is absent, never blanked (CO-18).

Adding an alert (`kind`, `text`, `sensitive`) and ending one with a reason both need `encounters.chart`, and both work offline (BM-96).

### 5.6 Who is shown a stock alert, and when
"The field user sees no alert during the run; the count goes negative, and the Program Admin, Logistics and the route lead are alerted" (PRD main 126). `alertVisibleTo` (5.3) decides it when the alert is read:
- A `below_minimum` alert whose minimum no longer holds (minimums off, the bag no longer carrying the item, or the bag's current minimum not above its balance) is `hidden` everywhere.
- **The portal**: `shown` to `inventory.view`, `held` while the reader is on an outing under way (a member, the lead included, of an outing of the team whose window holds now and that is not ended: `outingUnderway`), as on a phone (BM-87). Every portal read that shows an alert asks it: Restock alerts, its count on Home, and the open alerts of the Inventory page and of a location's page. Balances are not alerts and show at any time: they are the stock record the people who restock read (PRD main 473, 475; 12).
- **A phone, and a push**: to whoever holds `inventory.manage` and to the lead of the alert's outing (PL-27): `held` while they are on an outing under way, `shown` otherwise. Everyone else: `hidden`.

So nobody on a run is shown a stock alert, on any surface and from any bag, and the lead sees their own run's once it is over (BM-86, BM-87).

Home's **Supplies to restock** number is the count of the phone's `shown` alerts (7). A push is queued, in the opening movement's transaction, for each person the phone surface gives `shown` or `held`, with `not_before` the end of their outing's window when held; one row per team, person, sentence and hour, so a burst is one push (`queuePush`). The drain asks again before it sends (7): the count it sends is the person's `shown` alerts at that moment; a person still on a run waits; one with none left, or who no longer holds the key, is dropped.

## 9. Audit events and the PHI rules that apply
Every event is written in the transaction of the change it records (`ctx.audit`, or the route's transaction). Details carry IDs, counts, codes and flags only. The chain can't be redacted (D41), so an event about a patient names neither the item nor the bag of an order, nor whether an alert is sensitive, for any of them: naming only the others would mark the sensitive ones by their absence, to a role that holds `team.view_audit` without the sensitive keys (CO-14's reasoning, phase 5). Nor does a stock alert's event, for any alert: one an order opens is written in the order's transaction, next to `order.created` in the team's chain with the same actor, device and request (`append_audit`, `db/migrations/0003`), so its item would be the item of that patient's order. The item and the bag are in the order's row, read by `orderVisibleTo`, and in the alert's, read on the portal by `inventory.view`.

| Event | Written when | Details |
|---|---|---|
| `order.created`, `order.voided` | The sync change applies | `changeId`, `quantity`, `source`, `flags`; patient ID in the event's own column |
| `order.allergy_override` | An order that carries an override is stored, whatever the server's re-check finds (5.4) | `allergyIds`, `reasonLength` (never the reason) |
| `order.flagged` | The server sets a review flag | `flags` |
| `inventory.alert_opened`, `.alert_closed` | `alertEffect` says so | `alertId`, `kind`, `balance`, `recipientCount`; never the item or the bag, for any alert; no patient, order or visit |
| `patient_alert.created`, `.ended` | The sync change applies | `kind` (never the text, never whether it is sensitive) |
| `inventory.recounted` | A correction | each line's `{itemId, before, after}`; never the reason, which stays with its movement (PL-14) |
| `inventory.log_viewed`, `order.review_viewed` | The supply log shows a visit; the review list is read | `patientIds`, `count` |
| Section 7's other events | As listed | As listed |

- The supply log is `stock_movements` itself: append-only, so it needs no second copy in the audit chain.
- An override reason, an alert's text, a void reason and a lab result are patient details. They live in their rows, reach only readers of the chart by the read rules of 5.1 and 5.5, and never enter audit details, logs, URLs, page titles, notices or pushes. A count's reason is not patient data but free text, kept with its movement and never audited (PL-14; the departure from PRD main 954 is 12's). The `order_flagged` notice is a kind and a record ID; `order_not_applied` and `patient_alert_not_applied` also name the patient, as `flag_change_not_applied` does; none holds text (lifecycle 4.10).
- A stock alert names a bag and an item, never a patient or an encounter. Home's number comes from `GET /v1/me/counts`, which names no patient, so opening Home logs none.
- Push sentences, each in the singular at 1: `stock_alert`: "Supplies to review" / "1 supply item needs a restock." or "{n} supply items need a restock."; `note_incomplete`: "Notes" / "A note is waiting to be finished." (reserved by phase 4, lifecycle 3.9); `tasks_due`: "Tasks" / "1 task due today" or "{n} tasks due today" (PRD main 746). Nothing queues the last two in this phase: both are worked out when read, and no scheduled job exists (PL-33). Phase 7 adds its route sentences to the list (PRD main 330); a sentence joins only by being added to it, in `services/api/src/push/messages.ts` and its vectors.

## 12. Risks, and where the design departs from the PRD or reads it a particular way
1. **Phase 5's leftovers change the code this phase builds on.** I0-sweep gives `EntityRules.load` the team, which both new entities implement; I0-held changes the sync engine and Needs attention, which I1 and I4 edit. They land first (13.1), and a unit that starts before them is rebased on them.
2. **The outing overlaps phase 7.** If phase 7 models routes differently, `bag_outings` becomes a view over routes. It is four small tables, chosen so that the Done when's "route lead", and who is on the run, are real now. Phase 7's design absorbs the outing with its lead as its only member (`docs/design/phase-7-routes-runs.md`, "The outing, absorbed"); with members stored here, it takes them as the route's members.
3. **Reading: "the field user sees no alert during the run" (PRD main 126)** means no stock alert, on the phone, in a push or on the portal, for anyone on an outing under way, whatever their role and whichever bag; the lead is alerted after their run, and the Program Admin and Logistics at once unless they are on one (BM-86, BM-87). The portal still shows balances to `inventory.view`, a count below zero included: they are the stock record the people who restock read (PRD main 473, 475), so a field user who opens the portal mid-run can see a balance below zero, though no alert. Under TM-37's window someone on tomorrow's outing sees no alert from the evening before, in the portal too.
4. **Departure: the phone shows no counts.** The PRD's "in-bag items" (main 125) is read as "items the bag lists". A shown count would turn negative and act as an alert. It holds on the Orders screen, the supply screen and during a run; phase 7's bag check at confirm is its one exception (main 476), and needs its own yes.
5. **Departure: an unsafe order is stored, not blocked, by the server.** The hard stop blocks on the phone (PRD main 497). The server cannot block what has been handed over; it flags it (CO-17).
6. **Reading: "needs a Medical encounter and an ordering credential" (PRD main 447) is enforced as phase 4 enforces Medical,** and "Only credentials allowed to order can place them" (main 450) as the phone's rule: the phone offers a Medical item only in a Medical visit and disables a medication for a credential that may not order; the server checks the credential, never the kind (D56), and flags what a lowered credential sent. "No orders" in Non-Medical work (main 379) is read as no Medical items; supplies still deduct.
7. **Text matching misses.** "PCN" matches only if an admin lists it as a word, and the platform ships none (BM-103). A miss shows no stop. The allergy badge stays on screen while ordering.
8. **The phone's test server grows a stock ledger** (plan risk 7). Its parity tests land with the rules they mirror, in I1b, and its reads' in I2.
9. **Push is unproven until accounts exist.** Everything up to the sender is tested; delivery is not, and production sends nothing until counsel answers (CO-16). A token left by a sign-out made offline goes only when that phone next signs in, so until then a push can reach a phone its person signed out of; it carries a fixed sentence only.
10. **Reading: "the route's bags" (PRD main 448, 475)** are the bags of the outing the person is on, and the bags they own that no outing takes that day (main 474).
11. **Reading: "before signing" (PRD main 471)** is the supply screen shown once at Complete when suggestions are untouched; an order can still be added or removed after signing (D57).
12. **Reading: the "alternative" of Build plan 97** is choosing another item of the category, the matching ones marked; the app recommends no drug (BM-92).
13. **Reading: "the team gets a restock reminder" (PRD main 477)** is the people alerted for a negative count (PL-27), and "low-stock warnings" (main 473) are bag minimums (BM-98).
14. **Departure: no push for the 24-hour alert (PRD main 99) or for tasks due (main 746)** until a scheduled job exists (PL-33; phase 12 design 11.1 #20). Both still show on Home and in the portal.
15. **Reading: an order's sensitivity follows its item, as a note's follows its type.** An item marked sensitive or treatment is read as phase 4 reads a sensitive note type or a treatment record; a hand-entered or bundled line has no note to be read by, so the item carries it (CO-19). An item a team forgets to mark is read as any other.
16. **A late order is placed around a count by its own time.** An order made offline with a clock off by a few minutes (within the clock pause's 5) can fall on the wrong side of a count taken in those minutes, and the count's balance is off by that order until the next count.
17. **The audit log names no item or bag for an order or a stock alert** (9). An audit search can tell that a patient was given something, and when, but not what; the chart and the supply log, under their read rules, can. An alert's event names its id and the alert's row names its item, so a custom role holding `team.view_audit` and `inventory.view` without `patients.view_sensitive` could still join an alert an order opened to that order's patient: CO-14's case, closed by giving `team.view_audit` only to roles that also hold the sensitive keys, as the standard roles do.
18. **Below-minimum reminders are read against the minimum now.** An alert opened under an old minimum is quiet while the current one does not hold, and shows again if a later minimum does, until the item's next movement closes or keeps it.
19. **Departure: a kit edit's reason is not in the audit log.** PRD main 954 says "the audit log records the old value, new value and reason" of a count changed, an item added or one taken off. Its events record the old and new values (`inventory.recounted`, `inventory.not_carried`); the reason is kept with its movement and shown in the supply log, which is append-only, since free text in the chain can't be redacted (D41, PL-14; PL-31).
20. **Reading: "the person (or Logistics, for a teammate) enters which items were added" (PRD main 960)** dates from personal kits, which shared bags replaced (main 474, Oct 12). A restock needs `inventory.manage`, so Logistics records it for any bag, its owner's included, and an owner without the key asks Logistics (BM-104).
21. **Reading: "Each entry records user, bag, item, quantity, reason and time" (PRD main 475)** is what every row holds. A reader who may not read an order is shown its movement's day only, without its user, time or visit, since those are its visit's author and minute, which the timeline shows that reader (CO-19).

### 13.4 The cards
Levels follow `docs/plan/README.md`. An always-X path is X: the API's `sync/`, `auth/` and `db/` code, the phone's `lib/sync/`, the phone's test server, a migration with policies or triggers, `.github/` and `tools/`. So is a card whose wrong line would lose a write, move stock twice or show something to the wrong reader where no other card's test would catch it: the stock movement writer, the read rule, the push outbox and drain, a token's going at a wipe. Each unit's tests card is X, since what it writes is what the T cards are held to, and so is the Done when's story. A screen or a page is R, and so are the contract cards, the seed and the tests that walk the Done when but the live one. `orderVisibleTo` and `alertVisibleTo` are T because `order-rules.json` and `stock-rules.json` pin them. A T card's tests are written first, by its unit's tests card. No row is S: none is left to a machine check alone. Levels say where review is strictest ("How this phase is built").

Short paths: `api/` is `services/api/src/`, `api-test/` is `services/api/test/`, `phone/` is `apps/mobile/lib/`, `phone-test/` is `apps/mobile/test/`, `presets/` is `packages/presets/`, `vectors/` is `packages/contract/test-vectors/`, `(app)/` is `apps/portal/src/app/(app)/`, `actions/` is `apps/portal/src/app/actions/`, `lib/` is `apps/portal/src/lib/`, `e2e/` is `apps/portal/e2e/`, `fake` is `phone-test/sync/fake_server.dart`. A file that does not exist yet is new; every other is edited. Migrations take the next free numbers, 0026 to 0030 if nothing lands between.
